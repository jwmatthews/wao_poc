# OpenShift-specific operator packaging requirements, certification, platform requirements, and webhooks/certificates under OLM v1 (state as of 2026-10-10)

Scope note: all facts below come from Red Hat official documentation (docs.redhat.com), Red Hat ecosystem GitHub repositories (redhat-openshift-ecosystem/*, openshift/*), or upstream operator-framework repositories. Where a Red Hat page was retrieved via its `html-single` rendering, the URL given is the one actually fetched. Observed documentation structure: the Operator SDK chapters ("Developing Operators" → "Defining cluster service versions (CSVs)", "Bundle validation", etc.) are present in the OCP 4.15 Operators guide, but the OCP 4.18/4.19/4.20 Operators guides fetched during this research no longer contain the `features.operators.openshift.io` annotation table, the multi-arch label section, or the `operator-sdk bundle validate` reference (the OCP 4.18 guide instead carries the notice that the Red Hat-supported Operator SDK CLI is deprecated). The Red Hat OpenShift Software Certification Policy Guide (2025) still links to the 4.15 version of these pages. Version applicability is therefore stated per finding.

## Key question 1: CSV/bundle metadata Red Hat requires or recommends for OpenShift

### Takeaway
Red Hat's OpenShift-specific CSV metadata is a stable set of `features.operators.openshift.io/*` boolean-string annotations (which replaced the deprecated `operators.openshift.io/infrastructure-features` array in OCP 4.14), `operators.openshift.io/valid-subscription`, `olm.properties` with `olm.maxOpenShiftVersion` (honored by both OLM (Classic) and OLM v1 through the `olm` ClusterOperator's `Upgradeable=False`), `operatorframework.io/arch.*`/`os.*` labels, `spec.relatedImages` by digest, and the bundle-image label/annotation `com.redhat.openshift.versions`; the certification policy guide makes most of these mandatory.

### Cited Findings
- `features.operators.openshift.io` annotations "detail the infrastructure features that an Operator might support, specified by setting a `"true"` or `"false"` value. Users can view and filter by these features when discovering Operators through OperatorHub in the web console or on the Red Hat Ecosystem Catalog. These annotations are supported in OpenShift Container Platform 4.10 and later." — [OCP 4.15 Operators guide, §5.7.3.1 "Infrastructure features annotations"](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Exact keys and documented meanings (all with valid values `"true"` or `"false"`; "Valid values are shown intentionally with double quotes, because Kubernetes annotations must be strings"):
  - `features.operators.openshift.io/disconnected` — "Specify whether an Operator supports being mirrored into disconnected catalogs, including all dependencies, and does not require internet access. The Operator leverages the `spec.relatedImages` CSV field to refer to any related image by its digest."
  - `features.operators.openshift.io/fips-compliant` — "Specify whether an Operator accepts the FIPS-140 configuration of the underlying platform and works on nodes that are booted into FIPS mode. In this mode, the Operator and any workloads it manages (operands) are solely calling the Red Hat Enterprise Linux (RHEL) cryptographic library submitted for FIPS-140 validation."
  - `features.operators.openshift.io/proxy-aware` — "Specify whether an Operator supports running on a cluster behind a proxy by accepting the standard HTTP_PROXY and HTTPS_PROXY proxy environment variables. If applicable, the Operator passes this information to the workload it manages (operands)."
  - `features.operators.openshift.io/tls-profiles` — "Specify whether an Operator implements well-known tunables to modify the TLS cipher suite used by the Operator and, if applicable, any of the workloads it manages (operands)."
  - `features.operators.openshift.io/token-auth-aws` — "tokenized authentication with AWS APIs via AWS Secure Token Service (STS) by using the Cloud Credential Operator (CCO)."
  - `features.operators.openshift.io/token-auth-azure` — "tokenized authentication with Azure APIs via Azure Managed Identity by using the Cloud Credential Operator (CCO)."
  - `features.operators.openshift.io/token-auth-gcp` — "tokenized authentication with Google Cloud APIs via GCP Workload Identity Foundation (WIF) by using the Cloud Credential Operator (CCO)."
  - `features.operators.openshift.io/cnf`, `features.operators.openshift.io/cni`, `features.operators.openshift.io/csi` — whether the Operator provides a CNF / CNI / CSI Kubernetes plugin. — [OCP 4.15 Operators guide, Table 5.9](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Example given in the docs:
  ```yaml
  apiVersion: operators.coreos.com/v1alpha1
  kind: ClusterServiceVersion
  metadata:
    annotations:
      features.operators.openshift.io/disconnected: "true"
      features.operators.openshift.io/fips-compliant: "false"
      features.operators.openshift.io/proxy-aware: "false"
      features.operators.openshift.io/tls-profiles: "false"
      features.operators.openshift.io/token-auth-aws: "false"
      features.operators.openshift.io/token-auth-azure: "false"
      features.operators.openshift.io/token-auth-gcp: "false"
  ```
  — [OCP 4.15 Operators guide, §5.7.3.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Deprecation: "Starting in OpenShift Container Platform 4.14, the `operators.openshift.io/infrastructure-features` group of annotations are deprecated by the group of annotations with the `features.operators.openshift.io` namespace. While you are encouraged to use the newer annotations, both groups are currently accepted when used in parallel." Deprecated valid values: `disconnected`, `cnf`, `cni`, `csi`, `fips`, `proxy-aware`; example `operators.openshift.io/infrastructure-features: '["disconnected", "proxy-aware"]'`. — [OCP 4.15 Operators guide, §5.7.3.2 / Table 5.10](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Other optional annotations (Table 5.11): `alm-examples`; `operatorframework.io/initialization-resource` ("Specify a single required custom resource ... Must include a template that contains a complete YAML definition"); `operatorframework.io/suggested-namespace` ("Set a suggested namespace where the Operator should be deployed"); `operatorframework.io/suggested-namespace-template` ("Set a manifest for a Namespace object with the default node selector"; "If both suggested-namespace and suggested-namespace-template annotations are present in the CSV, suggested-namespace-template should take precedence"); `operators.openshift.io/valid-subscription` ("Free-form array for listing any specific subscriptions that are required to use the Operator. For example, '["3Scale Commercial License", "Red Hat Managed Integration"]'"; example for OCP: `operators.openshift.io/valid-subscription: '["OpenShift Container Platform"]'`); `operators.operatorframework.io/internal-objects` ("Hides CRDs in the UI that are not meant for user manipulation"; example `operators.operatorframework.io/internal-objects: '["my.internal.crd1.io","my.internal.crd2.io"]'`). — [OCP 4.15 Operators guide, §5.7.3.3, §5.7.6–5.7.8](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Required manually-defined CSV fields (Table 5.7): `metadata.name`, `metadata.capabilities` ("The capability level according to the Operator maturity model. Options include Basic Install, Seamless Upgrades, Full Lifecycle, Deep Insights, and Auto Pilot."), `spec.displayName`, `spec.description`, `spec.keywords`, `spec.maintainers`, `spec.provider`, `spec.labels`, `spec.version`, `spec.customresourcedefinitions`. — [OCP 4.15 Operators guide, §5.7.2](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- `olm.maxOpenShiftVersion` (OLM (Classic) docs): "In your Operator project's cluster service version (CSV), set the `olm.maxOpenShiftVersion` annotation to prevent administrators from upgrading their cluster before upgrading the installed Operator to a compatible version"; "You must use `olm.maxOpenShiftVersion` annotation only if your Operator bundle version cannot work in later versions. Be aware that cluster admins cannot upgrade their clusters with your solution installed. If you do not provide later version and a valid upgrade path, administrators may uninstall your Operator and can upgrade the cluster version." Syntax: `"olm.properties": '[{"type": "olm.maxOpenShiftVersion", "value": "<cluster_version>"}]'`. — [OCP 4.15 Operators guide, §5.7.x "Controlling Operator compatibility with OpenShift Container Platform versions"](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- `olm.maxOpenShiftVersion` under OLM v1 (OCP 4.21): "In the Operator project's cluster service version (CSV), authors can set the `olm.maxOpenShiftVersion` annotation to prevent administrators from updating the cluster before updating the installed Operator to a compatible version." "Replace `<cluster_version>` with the latest minor version of OpenShift Container Platform (4.y) that an Operator is compatible with. For example, setting value to `4.21` prevents cluster updates to minor versions later than 4.21 when this bundle is installed on a cluster." "If the `olm.maxOpenShiftVersion` field is omitted, cluster updates are not blocked by this Operator." "When determining a cluster's next minor version (4.y+1), OLM v1 only considers major and minor versions (x and y) for comparisons. It ignores any z-stream versions (4.y.z) ... or pre-release versions." "If an installed Operator's `olm.maxOpenShiftVersion` field is set and a cluster administrator attempts to update their cluster to a version that the Operator does not provide a valid update path for, the cluster update fails and the `Upgradeable` status for the `olm` cluster Operator is set to `False`." — [OCP 4.21 Extensions guide, §5.5.5 and §5.5.5.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- The OCP 4.20 Operators guide's cluster Operators reference says the OLM v1 `olm` cluster Operator "informs cluster administrators if there are any installed extensions blocking cluster upgrade, based on their `olm.maxOpenShiftVersion` properties", and the OLM (Classic) `operator-lifecycle-manager` cluster Operator does the same for installed Operators. — [OCP 4.20 Operators guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/operators/index)
- Community/certified pipeline guidance on `olm.maxOpenShiftVersion` and `com.redhat.openshift.versions`: "Use the `olm.openShiftMaxVersion` annotation in the CSV [sic; the YAML shown is `"olm.properties": '[{"type": "olm.maxOpenShiftVersion", "value": "4.8"}]'`] to prevent the user from upgrading their OCP cluster before upgrading the installed operator version"; "Use the annotation `com.redhat.openshift.versions` in `bundle/metadata/annotations.yaml` to ensure that the index image will be generated with its OCP Label ... `com.redhat.openshift.versions: "v4.6-v4.8"` ... the Operator will not appear in a catalog of an Openshift version that is outside of the range. You must use it if you are distributing a solution that contains deprecated API(s)". — [operator-pipelines docs/users/packaging-required-criteria-ocp.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/packaging-required-criteria-ocp.md)
- `com.redhat.openshift.versions` syntax (certification policy guide, Operator requirements table): "The Operator bundle must indicate the minor versions of OpenShift that the target product supports by setting the `com.redhat.openshift.versions` annotation. Annotation syntax: a) Restrict to a single RHOCP version: `"=v4.17"` b) Restrict to a version range: `"v4.16-v4.17"` c) Open-ended version range: `"v4.16"`. If the open-ended version range listed is deprecated, the operator bundle will only appear in the fully supported and maintained versions. The version range must include one or more current RHOCP versions, that are in the Full Suport, Maintenance Support, EUS, or EUS Term 2 life cycle phases. The range may directly or implicitly include one or more future versions of RHOCP. Upon the release of a new RHOCP minor version, Operators with ranges that include the new minor version and are in good standing regarding the lifecycle and recertification policies, will automatically be certified and published for the new minor version of RHOCP." — [Red Hat OpenShift Software Certification Policy Guide (2025), §3.1](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_openshift_software_certification_policy_guide/index)
- Same label in the Workflow Guide: "In this file [`annotations.yaml`] include an annotation of OpenShift versions ... `# OpenShift annotations com.redhat.openshift.versions: v4.8-v4.10` ... Note that the letter 'v' must be used before the version, and spaces are not allowed. ... A single version indicates that the operator is supported on that version of OpenShift or later ... A single version preceded by '=' indicates that the operator is supported only on that specific version ... A range can be used to indicate support only for OpenShift versions within that range." — [Red Hat Software Certification Workflow Guide (2025), §22.2.2](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_software_certification_workflow_guide/index)
- Certification-required CSV `metadata.annotations` (policy guide): `categories`, `description`, `containerImage` ("The full location (registry, repository, name, and tag) of the Operator image"), `createdAt`, `support`, `operators.openshift.io/valid-subscription`, `features.operators.openshift.io/disconnected`, `features.operators.openshift.io/fips-compliant`, `features.operators.openshift.io/proxy-aware`, `features.operators.openshift.io/tls-profiles`, `features.operators.openshift.io/token-auth-aws`, `features.operators.openshift.io/token-auth-azure`, `features.operators.openshift.io/token-auth-gcp`; optional `features.operators.openshift.io/cnf`, `/cni`, `/csi`. Also: "The CSV in the Operator bundle must indicate all the container images needed to perform its function, using the `spec.relatedImages` field." and "The CSV in the Operator bundle must indicate all the CRDs Owned by the Operator." and "The Operator must update the status field of each custom resource (CR)." and "The Operator bundle must successfully pass the Operator SDK bundle validation." and "The Operator name must be different from any other Operator name already published in the Community, Certified, and Red Hat catalogs. The Operator name must not begin with a Red Hat Mark." — [Policy Guide §3.1](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_openshift_software_certification_policy_guide/index)
- Disconnected requirements (OLM (Classic) docs): "Replace hard-coded image references with environment variables. In the cluster service version (CSV) of your Operator: List any related images ... Reference all specified images by a digest (SHA) and not by a tag. All dependencies of your Operator must also support running in a disconnected mode. Your Operator must not require any off-cluster resources." Procedure uses `RELATED_IMAGE_<NAME>` env vars in `config/manager/manager.yaml`, `make bundle USE_IMAGE_DIGESTS=true` (operator-sdk `--use-image-digests`). — [OCP 4.15 Operators guide, §5.7.4](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Multi-arch labels: `operatorframework.io/arch.<arch>: supported` and `operatorframework.io/os.<os>: supported` in CSV `metadata.labels`; "If a CSV does not include an os label, it is treated as if it has ... `operatorframework.io/os.linux: supported`"; "If a CSV does not include an arch label, it is treated as if it has ... `operatorframework.io/arch.amd64: supported`"; "After you add a new architecture or operating system, you must also now include the default `os.linux` and `arch.amd64` variants explicitly"; "To support listing multiple architectures and operating systems, your Operator image referenced in the CSV must be a manifest list image"; "Only the labels on the channel head of the default channel are considered for filtering package manifests by label." — [OCP 4.15 Operators guide, §5.7.5](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- `operator-sdk bundle validate` multi-arch check output example: "check if the CSV is missing the label (operatorframework.io/arch.<value>) for the Arch(s): ["amd64" "arm64" "ppc64le" "s390x"] ... if you support more than amd64 architectures, you MUST,use the required labels for all which are supported." Command: `operator-sdk bundle validate ./bundle --select-optional name=multiarch`. — [OCP 4.15 Operators guide, §5.12.4](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index)
- Certification is "awarded to a single architecture. Apply for multiple certifications if your product supports more than one architecture." Supported: "x86_64, s390x, ppc64, and aarch64." — [Policy Guide §1.8](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_openshift_software_certification_policy_guide/index)
- `operatorhub.io/ui-metadata-max-k8s-version: "<version>"` CSV annotation informs the maximum supported Kubernetes version (community pipeline docs). — [operator-pipelines operator-ci-yaml.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/operator-ci-yaml.md)
- Catalog-source namespace labels used by Red Hat for OLM (Classic) catalogs: `openshift.io/cluster-monitoring: "true"`, `security.openshift.io/scc.podSecurityLabelSync: "false"`, `pod-security.kubernetes.io/enforce: baseline` (example namespace YAML for a catalog that cannot run restricted). — [OCP 4.20 Operators guide, §4.9.4](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/operators/index)

### Inferences
- A bundle that must serve both OLM (Classic) and OLM v1 should set the full `features.operators.openshift.io/*` set explicitly (the certification table treats the seven non-plugin keys as required), keep `operators.openshift.io/infrastructure-features` only for OCP < 4.14 compatibility, and set `olm.maxOpenShiftVersion` only when a bundle genuinely cannot run on the next minor version, because OLM v1 enforces it with identical semantics (it blocks the cluster update via `olm` ClusterOperator `Upgradeable=False`).
- `com.redhat.openshift.versions` is a catalog-inclusion control enforced by the Red Hat pipeline/index build (not by OLM at runtime), so a WAO-style operator targeting 4.18–4.21 would use `com.redhat.openshift.versions: "v4.18-v4.21"` or open-ended `"v4.18"` if it wants automatic inclusion in future catalogs.

### Gaps
- `com.redhat.delivery.operator.bundle` and `com.redhat.delivery.backport` bundle-image labels: no Red Hat documentation page defining them was found in the sources fetched (the certified-operator gitbook redirected to a GitBook app URL and could not be read). Their semantics are not confirmed here.
- `operatorframework.io/cluster-monitoring` and `console.openshift.io/*` CSV annotations: not documented in any of the OCP 4.15/4.18/4.19/4.20/4.21 Operators or Extensions guides fetched. Only the namespace label `openshift.io/cluster-monitoring: "true"` (for catalog namespaces) and the `console.openshift.io/v1` API group (ConsoleLink, ConsolePlugin, ConsoleQuickStart, etc.) appear.
- `spec.minKubeVersion` is not discussed in the OpenShift docs fetched; no OpenShift-specific requirement for it was found.
- The OCP 4.18+ docs no longer carry the SDK annotation tables; whether Red Hat has republished them elsewhere (for example in the Certified Operator Guide gitbook) could not be verified because that site redirected to an authenticated GitBook app URL.

## Key question 2: Red Hat certification (Partner Connect / certified-operators) and community-operators-prod requirements that affect OLM v1

### Takeaway
Both the certified and community pipelines are now File-Based-Catalog-first: the operator author owns per-OCP-version catalog templates (`catalog-templates/`, `olm.semver` or `olm.template.basic`) mapped to `catalogs/v4.x` through `ci.yaml` (`fbc.enabled`, `fbc.catalog_mapping`, `fbc.version_promotion_strategy`), the bundle must pass `operator-sdk bundle validate` plus preflight (`preflight check operator`, which includes `DeployableByOLM` on a live OLM (Classic) cluster), and no OLM v1-specific lint step or published "OLM v1 readiness" checklist was found in any Red Hat source.

### Cited Findings
- `ci.yaml` options (operator-pipelines docs): `reviewers` (community only; "If the author of PR will be in that list, changes she/he made will be taken as authorized changes ... ready to merge automatically"); `fbc.enabled` ("enables the File-Based catalog feature. It is highly recommended to use the FBC mode"); `fbc.version_promotion_strategy` with values `review-needed` (default: promoted to next OCP version automatically but a PR is created for review), `always`, `never`; `fbc.catalog_mapping` ("link between catalog templates within the `./catalog-templates` directory and catalogs within the `./catalogs` directory"); `updateGraph` ("only available for the non-FBC operators") with `replaces-mode` ("Every next version defines which version will be replaced using `replaces` key in the CSV") and `semver-mode` ("Every version will be replaced by the next higher version according to semantic versioning"; "By default, `replaces-mode` is activated, when `ci.yaml` file is present and contains `updateGraph: replaces-mode`. When a contributor decides to switch and use `semver-mode`, it will be specified in `ci.yaml` file or the key `updateGraph` will be missing."); `cert_project_id` ("required for certified and marketplace operators"). — [operator-pipelines docs/users/operator-ci-yaml.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/operator-ci-yaml.md)
- `ci.yaml` FBC example verbatim:
  ```yaml
  fbc:
    enabled: true
    version_promotion_strategy: never
    catalog_mapping:
      - template_name: my-custom-semver-template.yaml # The name of the file inside ./catalog-templates directory
          catalogs_names: # a list of catalogs within the /catalogs directory
            - "v4.15"
            - "v4.16"
            - "v4.17"
          type: olm.semver
      - template_name: my-custom-basic-template.yaml
          catalogs_names:
            - "v4.12"
            - "v4.13"
          type: olm.template.basic
  ```
  — [operator-ci-yaml.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/operator-ci-yaml.md)
- FBC workflow: "The OPM currently supports 2 types of templates ... Basic template - `olm.template.basic`; SemVer template - `olm.semver` ... The recommended template from the maintainability point of view is `SemVer`." Directory layout: `<version>/manifests`, `<version>/metadata`, `<version>/release-config.yaml`, `catalog-templates/`, `ci.yaml`, `Makefile` (downloaded with `wget https://raw.githubusercontent.com/redhat-openshift-ecosystem/operator-pipelines/main/fbc/Makefile`); "In case an operator isn't shipped to all OCP catalog versions manually update `OCP_VERSIONS` variable in the `Makefile`"; `make catalogs` renders templates to `catalogs/v4.x/<operator>/catalog.yaml`; "Currently a workflow requires a 2-step process to release a new bundle into the catalog ... the operator bundle is released and in the second step, the catalog is updated"; automated release ("fbc auto-release") requires the SemVer template; "A great benefit of FBC is that users can update operator update graphs independently of operator releases." — [operator-pipelines docs/users/fbc_workflow.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/fbc_workflow.md)
- SemVer template example in Red Hat docs uses channels `Candidate`, `Fast`, `Stable` with `GenerateMajorChannels: true` and `GenerateMinorChannels: true`. — [fbc_workflow.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/fbc_workflow.md)
- Certification workflow guide: "Use File-Based Catalog workflow for all new operator certifications and to convert all the existing certified operators to a more scalable, template-driven format." "You should convert your operator to the FBC format before submitting it through the certification workflow." Onboarding command: `make fbc-onboarding` after downloading the Makefile. Required repo files: `config.yaml` (`organization: certified-operators`), `ci.yaml` (`cert_project_id: <your component pid>`), `metadata/annotations.yaml` with `com.redhat.openshift.versions`. — [Workflow Guide §22.2–22.4](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_software_certification_workflow_guide/index)
- Bundle validation for OpenShift catalogs: "you can check the bundle via `operator-sdk bundle validate` against the suite Validator Community Operators and the K8s Version that you are intended to publish: `operator-sdk bundle validate ./bundle --select-optional suite=operatorframework --optional-values=k8s-version=1.22`" and the experimental `ocp-olm-catalog-validator my-bundle-path/bundle --optional-values="file=bundle-path/bundle/metadata/annotations.yaml"`, whose sample error reads "olm.maxOpenShiftVersion csv.Annotations not specified with an OCP version lower than 4.9 ... or provide compatible version(s) via the labels. (e.g. LABEL com.redhat.openshift.versions='4.6-4.8')". — [packaging-required-criteria-ocp.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/packaging-required-criteria-ocp.md)

## Key question 3: OpenShift platform requirements for operator workloads

### Takeaway
On OpenShift the operator Deployment must run under the `restricted-v2` SCC/restricted PSA profile (global PSA enforces `privileged` but warns/audits `restricted`, with SCC-to-PSA label sync on non-`openshift-*` namespaces), should be FIPS-capable by building with Red Hat Go Toolset (`CGO_ENABLED=1`, dynamic linking, `GOEXPERIMENT=strictfipsruntime`), must handle `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` and propagate them to operands (OLM (Classic) injects them automatically; no equivalent is documented for OLM v1), may consume the cluster CA bundle through a ConfigMap labeled `config.openshift.io/inject-trusted-cabundle: "true"`, and since OCP 4.20 may ship its own `NetworkPolicy` manifests in the bundle for OLM v1.

### Inferences
- For OLM v1 installs there is no `Subscription.spec.config` surface, so proxy env vars and CA-bundle mounts must be baked into the bundle's Deployment (or the operator must read the cluster `Proxy` object itself); the only OLM v1 mechanism for post-install Deployment customization is the upstream alpha `DeploymentConfig` gate, which OCP 4.21 ships disabled.
- Since OLM v1 namespaces are created by the admin (the `ClusterExtension.spec.namespace`), operator authors should document the namespace labels they expect (for example `openshift.io/cluster-monitoring: "true"` and no `pod-security.kubernetes.io/enforce` override), and ship `NetworkPolicy` manifests in the bundle for OCP 4.20+.
- A bundle whose Deployment sets `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, `seccompProfile.type: RuntimeDefault` and does not set `runAsUser` will satisfy `restricted-v2` (MustRunAsRange assigns the UID); this is inferred from the SCC table, not stated as a checklist in the docs.

## Key question 4: Webhooks and certificates on OpenShift under OLM v1

### Takeaway
OLM v1 provisions webhook TLS through a pluggable certificate provider selected by operator-controller feature gates (`WebhookProviderCertManager` upstream default; `WebhookProviderOpenshiftServiceCA` on OpenShift); on OCP the cluster-olm-operator maps the OpenShift FeatureGate `NewOLMWebhookProviderOpenshiftServiceCA` to `--feature-gates=WebhookProviderOpenshiftServiceCA=true` and forces `WebhookProviderCertManager=false`, so the bundle needs nothing beyond a standard CSV `spec.webhookdefinitions`; webhook extensions were "Not Available" in 4.19, Technology Preview (TechPreviewNoUpgrade) in 4.20, and GA in 4.21.

### Inferences
- Red Hat's OpenShift implementation does not require cert-manager for OLM v1 webhooks: on OCP 4.21 the Service CA path is GA and is what the docs describe. The exact Service CA annotation keys (`service.beta.openshift.io/serving-cert-secret-name`, `service.beta.openshift.io/inject-cabundle`) are not spelled out in the 4.21 Extensions guide, which only says "Applies Service CA annotations to webhook configurations and services"; these are the standard Service CA annotations documented elsewhere in OCP and are the natural reading of that sentence, but they were not verbatim-confirmed in an OLM v1 source during this research.
- Because both webhook gates default to `true` in the 4.21 downstream `features.go` and `getCertificateProvider` prefers CertManager, the cluster-olm-operator's explicit `WebhookProviderCertManager=false` mapping is what makes OpenShift select Service CA; any manual deployment of operator-controller on OpenShift outside cluster-olm-operator would need `--feature-gates=WebhookProviderCertManager=false,WebhookProviderOpenshiftServiceCA=true` to get the documented behaviour.
- For the WAO bundle: keep `spec.webhookdefinitions` exactly as for OLM (Classic), keep `failurePolicy: Fail`, require `AllNamespaces: supported: true`, and do not hard-code the OLM (Classic) cert mount path assumptions in the operator binary unless it also tolerates the OLM v1-mounted secret; the OLM v1 mount path/secret naming was not found in docs (see Gaps).

### Gaps
- The exact mount path and secret name OLM v1 uses when it "Mounts certificate secrets to the Operator deployment", and whether it matches OLM (Classic)'s `/apiserver.local.config/certificates/`, was not found in the OCP docs or the upstream how-to; it would have to be read from operator-controller's `certproviders` render code.
- The openshift/api definition of `NewOLMWebhookProviderOpenshiftServiceCA` (which feature set it belongs to in 4.21, i.e. whether it is in `Default`) was not fetched; the 4.21 release-note table (GA) and the cluster-olm-operator mapping are the evidence relied on.
- No Red Hat statement was found on whether conversion-webhook CRDs under OLM v1 are subject to the same CRD-upgrade-safety preflight exceptions.

## Key question 5: Operator SDK / kubebuilder scaffolding guidance in 2026

### Takeaway
Operator SDK has no OLM v1 target: `operator-sdk olm install|status|uninstall` and `run bundle` still target OLM (Classic), the scaffolded Makefile `catalog-build` target still runs the deprecated `opm index add --mode semver`, and Red Hat has deprecated its supported Operator SDK CLI; the recommended replacement for catalogs is FBC (`opm init`/`opm render`/`opm generate dockerfile` or the operator-pipelines FBC Makefile with `olm.semver` templates).

### Cited Findings
- Red Hat deprecation: "The Red Hat-supported version of the Operator SDK CLI tool, including the related scaffolding and testing tools for Operator projects, is deprecated and is planned to be removed in a future release of OpenShift Container Platform. Red Hat will provide bug fixes and support for this feature during the current release lifecycle, but this feature will no longer receive enhancements ... The following related base images for Operator projects are not deprecated." — [OCP 4.18 Operators guide (notice repeated in each Operator SDK section)](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html-single/operators/index)
- Upstream scaffold (`testdata/go/v4/memcached-operator/Makefile`, `OPERATOR_SDK_VERSION ?= v1.42.3`): `catalog-build: opm ## Build a catalog image.` runs `$(OPM) index add --container-tool $(CONTAINER_TOOL) --mode semver --tag $(CATALOG_IMG) --bundles $(BUNDLE_IMGS) $(FROM_INDEX_OPT)`; `USE_IMAGE_DIGESTS ?= false` adds `--use-image-digests` to `operator-sdk generate bundle`; `BUNDLE_GEN_FLAGS ?= -q --overwrite --version $(VERSION) $(BUNDLE_METADATA_OPTS)`. — [operator-sdk testdata Makefile](https://github.com/operator-framework/operator-sdk/blob/master/testdata/go/v4/memcached-operator/Makefile)
- OpenShift: "The opm subcommands, flags, and functionality related to the SQLite database format are also deprecated and will be removed in a future release"; "As of OpenShift Container Platform 4.11, the default Red Hat-provided Operator catalog releases in the file-based catalog format"; "You can use the opm CLI to create a catalog image that uses the plain text file-based catalog format (JSON or YAML), which replaces the deprecated SQLite database format"; "As of OpenShift Container Platform 4.11, the `run bundle` command supports the file-based catalog format for Operator catalogs by default ... It is recommended that Operator authors migrate their workflows to the file-based catalog format." — [OCP 4.18 Operators guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html-single/operators/index)
- Operator SDK OLM integration docs list only `operator-sdk olm install`, `operator-sdk olm status`, `operator-sdk olm uninstall`, `operator-sdk run bundle`, `operator-sdk run bundle-upgrade`; no OLM v1/ClusterExtension content. — [sdk.operatorframework.io/docs/olm-integration/](https://sdk.operatorframework.io/docs/olm-integration/)
- Red Hat pipelines provide the FBC Makefile (`make catalogs`, `make fbc-onboarding`) and templates (`olm.semver` recommended). — [fbc_workflow.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/fbc_workflow.md); [Workflow Guide §22.3–22.4](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_software_certification_workflow_guide/index)
- OCP 4.21: "For OpenShift Container Platform 4.21, documented procedures for OLM v1 are CLI-based only ... the existing Software Catalog and Installed Operators pages do not yet display OLM v1 components." and "Currently in Operator Lifecycle Manager (OLM) v1, you cannot query on-cluster catalogs managed by catalogd. In OLM v1, you must use the `opm` and `jq` CLI tools to query the catalog registry." — [OCP 4.21 Extensions guide §5.2, §5.2.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)

### Inferences
- Projects should replace the scaffolded `catalog-build` with an FBC build (`opm init` + `opm render` of the bundle image, or `opm alpha render-template semver`) so the same catalog image can be used as an OLM (Classic) `CatalogSource` and an OLM v1 `ClusterCatalog`; the operator-pipelines `fbc/Makefile` is the Red Hat-maintained reference.

### Gaps
- No operator-sdk or kubebuilder plugin or subcommand for OLM v1 (ClusterExtension/ClusterCatalog) was found in the sources fetched; kubebuilder's plugin list was not examined directly.
- The upstream operator-sdk README was fetched but contained no maintenance/deprecation banner matching the grep terms, so the upstream project's support status is not characterised here.

## Key question 6: Supporting OLM v0 and v1 from one bundle, channel naming, and user docs

### Takeaway
Red Hat documents OLM v1 as consuming the same `registry+v1` bundles and FBC catalogs as OLM (Classic), with `replaces`/`skips`/`skipRange` honoured but successor selection by highest semver rather than channel-head proximity, no automatic major-version updates, and `ClusterExtension` CLI-only installation in 4.21; no Red Hat channel-naming convention for OLM v1 was found beyond the examples (`stable`, `pipelines-1.14`, `latest`, and the pipeline's `Candidate`/`Fast`/`Stable` semver channels).

### Cited Findings
- "Operator Lifecycle Manager (OLM) v1 supports OLM (Classic) semantics for update paths, also known as upgrade edges or upgrade constraints. Support includes `replaces`, `skips`, and `skipRange` directives, with a few noted differences." "In OLM (Classic), the successor closest to the channel head is chosen. In OLM v1, the successor with the highest semantic version (semver) is chosen." — [OCP 4.21 Extensions guide §5.5](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- "OLM v1 does not support automatic updates to the next major version or rollbacks to an earlier version. If you want to perform a major version update or rollback, you must verify and force the update manually." — [OCP 4.21 Extensions guide §5.5](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- "If you specify a channel in the CR, OLM v1 installs the latest version of the Operator or extension that can be resolved within the specified channel. When updates are published to the specified channel, OLM v1 automatically updates to the latest release that can be resolved from the channel." `spec.source.catalog.channels` "Specifies channel names as an array, such as `pipelines-1.14` or `latest`. This field is optional." — [OCP 4.21 Extensions guide §5.2/§5.5](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Example `ClusterExtension` (4.21):
  ```yaml
  apiVersion: olm.operatorframework.io/v1
  kind: ClusterExtension
  metadata:
    name: <extension_name>
  spec:
    namespace: <namespace_name>
    config:
      configType: Inline
      inline:
        watchNamespace: <namespace_name>
    serviceAccount:
      name: <service_account_name>
    source:
      sourceType: Catalog
      catalog:
        packageName: <package_name>
        channels:
          - <channel>
        version: "<version>"
  ```
  — [OCP 4.21 Extensions guide §2.2](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Red Hat-provided catalogs are queried for OLM v1 with `opm render registry.redhat.io/redhat/redhat-operator-index:v4.21 | jq ...` (same index image as OLM (Classic)). — [OCP 4.21 Extensions guide §5.2.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- OLM v1 background: "OpenShift Container Platform 4.18 includes components for a next-generation iteration of OLM as a generally available feature, which is known during this phase as OLM v1 ... Starting in OpenShift Container Platform 4.17, documentation for OLM v1 has been moved to the new guide, 'Extensions (OLM v1)'." — [OCP 4.21 Operators guide, Chapter 7](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/operators/olm-v1)
- Community pipeline semver template channels: `Candidate`, `Fast`, `Stable` with `GenerateMajorChannels: true`/`GenerateMinorChannels: true`; basic template example uses a `stable` channel with `replaces`. — [fbc_workflow.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/fbc_workflow.md)
- OLM (Classic)-only bundle features that OLM v1 ignores or rejects and therefore should not be relied on by a dual-mode bundle: `OperatorConditions` API ("If an extension relies on only the OperatorConditions API to manage updates, the extension might not install correctly ... As a workaround, you can pin your extension to a specific version"), FBC dependency properties, `APIService`s (upstream). — [OCP 4.21 Extensions guide §5.1.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index); [olmv1_limitations.md](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)

### Inferences
- A single `registry+v1` bundle published through the FBC pipeline (semver template) satisfies both runtimes as long as the CSV supports `AllNamespaces`, avoids `OperatorConditions`, dependencies, and `APIService`s, and its update graph is monotonic in semver (because OLM v1 picks the highest-semver successor, non-semver "latest" edges in a channel will behave differently than under OLM (Classic)).
- User documentation should give both an OperatorHub/`Subscription` path and a `ClusterExtension` YAML (with the pre-created namespace, ServiceAccount and RBAC it requires), because OCP 4.21 offers no console install path for OLM v1.

### Gaps
- No Red Hat guidance on channel naming (`stable` vs `stable-v1` vs versioned) specific to OLM v1 was found; the docs only show examples.
- The Red Hat blog "Announcing OLM v1: next-generation Operator Lifecycle Management" could not be fetched (HTTP 404 at the English URL), so its ISV guidance is not captured here.
