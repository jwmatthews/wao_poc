Scope note: upstream facts come from the operator-controller `main` branch at commit `8ab554bd18748cc1941593e00806dfef7892acb2` (2026-10-09), its release tags (latest `v1.12.0`, 2026-09-23), and the operator-registry / operator-framework/api / operator-sdk / Helm sources. ## Q1. Which registry+v1 features does OLM v1 support, restrict, or reject?

### Takeaway
OLM v1 installs only `registry+v1` bundles, requires `AllNamespaces` install mode unless the alpha `SingleOwnNamespaceInstallSupport` gate is on, rejects catalog-level dependency properties (`olm.gvk.required`, `olm.package.required`, `olm.constraint`), rejects `apiservicedefinitions.owned`, supports validating/mutating/conversion webhooks (GA upstream since v1.6.0, GA on OCP 4.21), and ignores `OperatorConditions`, `spec.minKubeVersion`, `relatedImages`, CSV-level `replaces`/`olm.skipRange` (the catalog channel entries are used instead), and the OperatorHub/OpenShift marketplace annotations.

### Cited Findings

**Bundle format and the three hard rules (upstream)**
- "Currently, OLM v1 only supports installing operators packaged in OLM v0 bundles, also known as `registry+v1` bundles. Additionally, the bundled operator, or cluster extension: **must** support installation via the `AllNamespaces` install mode. ... **must not** declare dependencies using any of the following file-based catalog properties: `olm.gvk.required`, `olm.package.required`, `olm.constraint`; **must not** define `APIService`s in the `ClusterServiceVersion`. OLM v1 verifies these criteria at install time and will surface violations in the `ClusterExtensions`'s `.status.conditions`." — [docs/project/olmv1_limitations.md](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)
- "OLM v1 supports `SingleNamespace` and `OwnNamespace` modes for `registry+v1` bundles for backwards compatibility with OLM v0, but these are not recommended install modes as there is a hard limitation of only one instance of a given CRD in the cluster." — [docs/project/olmv1_limitations.md](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)
- "OLM v1 does not support the `OperatorConditions` API introduced in legacy OLM. Currently, there is no testing to validate against this constraint. If an extension uses the `OperatorConditions` API, the extension does not install correctly. Most extensions that rely on this API fail at start time, but some might fail during reconcilation." — [docs/project/olmv1_limitations.md](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)

**Install-mode enforcement in code (exact error strings)**
- The manifest provider rejects bundles before rendering: `unsupported bundle: apiServiceDefintions are not supported` (when `len(rv1.CSV.Spec.APIServiceDefinitions.Owned) > 0`); `unsupported bundle: webhookDefinitions are not supported` (when webhook support is disabled) / `unsupported bundle: webhookDefinitions are not supported: certificate provider is nil`; `unsupported bundle: bundle does not support AllNamespaces install mode` (when `SingleOwnNamespaceInstallSupport` is off and `AllNamespaces` is not `supported: true`); `unsupported bundle: bundle must support at least one of [AllNamespaces SingleNamespace OwnNamespace] install modes`; and `spec.namespace is required unless the BoxcutterRuntime feature gate is enabled`. — [internal/operator-controller/applier/provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go)
- `MultiNamespace` is never reachable from the public API: the render-time validator accepts a multi-namespace target set only if the bundle supports `MultiNamespace`, but the bundle config schema exposes a single string `watchNamespace`; the renderer defaults the target namespace list to `[""]` (all namespaces) only when `AllNamespaces` is supported, otherwise returns `nil` and errors `exactly one target namespace must be specified` / `at least one target namespace must be specified`. — [internal/operator-controller/rukpak/render/render.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/render.go); [internal/operator-controller/rukpak/bundle/registryv1.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/registryv1.go)
- Render-time target namespace errors: `supported install modes %v do not support targeting all namespaces`, `supported install modes %v do not support targeting own namespace`, `supported install modes %v do not support target namespaces %v`, wrapped as `invalid target namespaces %v: ...`. — [render.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/render.go)

**Single/Own namespace: the `watchNamespace` config mechanism**
- "This feature is still in *alpha*. The `SingleOwnNamespaceInstallSupport` feature-gate is disabled by default and must be enabled" via `--feature-gates=SingleOwnNamespaceInstallSupport=true`. "A `ClusterExtension` can be configured to install bundle in `Single-` or `OwnNamespace` mode through the `.spec.config.inline.watchNamespace` property ... if the bundle: only supports *AllNamespaces* mode => `watchNamespace` is not a configuration; supports *AllNamespaces* and *SingleNamespace* and/or *OwnNamespace* => `watchNamespace` is optional; bundle only supports *SingleNamespace* and/or *OwnNamespace* => `watchNamespace` is required. The `watchNamespace` configuration can only be the install namespace if the bundle supports the *OwnNamespace* install mode, and it can only be any other namespace if the bundle supports the *SingleNamespace* install mode." — [docs/draft/howto/single-ownnamespace-install.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/single-ownnamespace-install.md)
- "users will not be able to install the same operator multiple times, and that in future iterations of the registry bundle format will not include *installModes*." — [docs/draft/howto/single-ownnamespace-install.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/single-ownnamespace-install.md)
- Config-validation error strings: `required field "watchNamespace" is missing`; `invalid value "X": watchNamespace must be "Y" (the namespace where the operator is installed) because this operator only supports OwnNamespace install mode`; `invalid value "X": watchNamespace must be different from "Y" (the install namespace) because this operator uses SingleNamespace install mode to watch a different namespace`; `unknown field "foo"`. Reported in the `Progressing` condition. — [docs/draft/howto/configure-bundles.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/configure-bundles.md)
- The schema is derived from the CSV's `spec.installModes`: "AllNamespaces only: remove watchNamespace ... OwnNamespace only: make watchNamespace required, must equal install namespace; SingleNamespace only: make watchNamespace required, must differ from install namespace; AllNamespaces + OwnNamespace: make watchNamespace optional". The base schema has `"additionalProperties": false` with only `watchNamespace` and `deploymentConfig` keys. — [internal/operator-controller/rukpak/bundle/registryv1.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/registryv1.go); [registryv1bundleconfig.json](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/registryv1bundleconfig.json)
- The `ClusterExtension.spec.config` union: `configType` "is required ... The only allowed value is "Inline"", and `inline` "must be a valid JSON/YAML object containing at least one property ... validated at runtime against a JSON schema provided by the bundle". CEL rule: `has(self.configType) && self.configType == 'Inline' ?has(self.inline) : !has(self.inline)`. — [api/v1/clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)
- How to inspect a bundle's install modes before choosing a config: `opm render <bundle-image> -o json | jq 'select(.schema == "olm.bundle") | .properties[] | select(.type == "olm.csv") | .value.spec.installModes'`. — [docs/draft/howto/configure-bundles.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/configure-bundles.md)
- Upstream attempted to promote the gate to GA on 2025-10-27 (`✨ Promote Single Own Feature Gate AND Config spec in the CR to GA (OPRUN-4098) (#2268)`) and reverted it on 2025-10-29 (`Revert "..." (#2292)`); `features.go` on main still lists `SingleOwnNamespaceInstallSupport: {Default: false, PreRelease: featuregate.Alpha}`. — [internal/operator-controller/features/features.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go); commit history of that file (git log, commits 3c2fcb4 and 760855f; both first appear in tag v1.6.0)

**Webhooks (validating, mutating, conversion)**
- "OLMv1 supports the installation of bundles containing webhooks by default. By default, OLM v1 uses the community Cert Manager package for admission webhook via the feature-gate flag `WebhookProviderCertManager`. To use the OpenShift Service CA provider, set the `--feature-gates=WebhookProviderOpenshiftServiceCA=true` flag at startup." Certificate (cert-manager provider) is self-signed, "Two validity period, rotating 24h before expiry", valid for `<service-name>.<namespace>`, `<service-name>.<namespace>.svc`, `<service-name>.<namespace>.svc.cluster.local`; for Openshift-ServiceCA "Generation and rotation are completely governed by Openshift-ServiceCA". "There's no change in the installation flow. Just install a bundle containing webhooks as you would any other." — [docs/draft/howto/enable-webhook-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/enable-webhook-support.md)
- Feature gates on main: `WebhookProviderCertManager: {Default: true, PreRelease: featuregate.GA}` and `WebhookProviderOpenshiftServiceCA: {Default: true, PreRelease: featuregate.GA}`. — [features.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go)
- Timeline: webhook support first merged 2025-05-14 (`:sparkles: Add support for installing bundles with webhooks (#1914)`) and the OpenShift Service CA provider 2025-05-15 (`Add openshift-serviceca certificate provider (#1969)`), both first released in v1.3.0 (2025-05-22); gates promoted to GA 2025-10-20 (`✨ Promote Webhook FeatureGates to GA (OPRUN-4098) (#2267)`), first released in v1.6.0 (2025-11-11). — git log of [features.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go), `git tag --contains`
- What the CSV must declare: webhooks come from `spec.webhookdefinitions[]` (`type` = `ValidatingAdmissionWebhook` | `MutatingAdmissionWebhook` | `ConversionWebhook`, `generateName`, `deploymentName`, `containerPort`, `targetPort`, `webhookPath`, `rules`, `failurePolicy`, `matchPolicy`, `objectSelector`, `sideEffects`, `timeoutSeconds`, `admissionReviewVersions`, `reinvocationPolicy`, `conversionCRDs`). Each of these fields is copied verbatim into the generated `ValidatingWebhookConfiguration` / `MutatingWebhookConfiguration` / CRD `spec.conversion`. Bundle authors must NOT ship their own `ValidatingWebhookConfiguration`/`MutatingWebhookConfiguration` manifests (not in the allowed-kinds list, see Q2). — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- Webhook validators (exact errors): `webhook of type '%s' with name '%s' references non-existent deployment '%s'`; `duplicate webhook '%s' of type '%s'`; `webhook of type '%s' has invalid name '%s': ...` (names must be DNS-1123 subdomains); `conversion webhook '%s' references custom resource definition '%s' not owned bundle`; `conversion webhooks [%s] reference same custom resource definition '%s'`; `bundle contains conversion webhook %q and supports install modes %v - conversion webhooks are only supported for bundles that only support AllNamespaces install mode`; `webhook %q contains forbidden rule: admission webhook rules cannot reference API group %q` (forbidden groups: `olm.operatorframework.io`, `*`); `webhook %q contains forbidden rule: admission webhook rules cannot reference resource %q for API group %q` (for `admissionregistration.k8s.io`: `*`, `mutatingwebhookconfiguration(s)`, `validatingwebhookconfiguration(s)`). — [validators/validator.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/validators/validator.go)
- Conversion-webhook CRDs: `custom resource definition '%s' must have .spec.preserveUnknownFields set to false to let API Server call webhook to do the conversion`; `custom resource definition '%s' is referenced by multiple conversion webhook definitions`. Conversion path defaults to `/`. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- Admission webhooks installed in Single/Own namespace mode get a `namespaceSelector` of `kubernetes.io/metadata.name In [<targetNamespaces>]`; in AllNamespaces mode no selector is set. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- Deployment certificate wiring: for any deployment serving a webhook, OLM v1 removes any existing volumes named `webhook-cert`/`apiservice-cert` or mounted at `/tmp/k8s-webhook-server/serving-certs` or `/apiserver.local.config/certificates`, and adds secret volumes for both paths from the cert secret with keys `tls.crt`/`tls.key` (webhook path) and `apiserver.crt`/`apiserver.key` (apiservice path). The operator must therefore read its serving cert from `/tmp/k8s-webhook-server/serving-certs/tls.crt|tls.key`. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- Cert provider details: cert-manager provider adds annotation `cert-manager.io/inject-ca-from: <ns>/<certName>` to webhook configs/CRDs/APIServices and creates an `Issuer` (`<certName>-selfsigned-issuer`, selfSigned) and a `Certificate` (name/secretName `<certName>`, duration 730d, renewBefore 24h, usages `server auth`, `isCA: false`). OpenShift Service CA provider adds `service.beta.openshift.io/serving-cert-secret-name: <certName>` on the Service and `service.beta.openshift.io/inject-cabundle: "true"` on webhook configs/CRDs/APIServices, creating no extra objects. — [certproviders/certmanager.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/certproviders/certmanager.go); [certproviders/openshift_serviceca.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/certproviders/openshift_serviceca.go)
- Naming parity with OLM v0: service name = `<deploymentName with "." replaced by "-">-service`, cert/secret name = `<serviceName>-cert`. — [render/certprovider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/certprovider.go)

**APIService (`apiservicedefinitions`)**
- Still rejected end-to-end on main: `unsupported bundle: apiServiceDefintions are not supported` in the provider. — [applier/provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go)
- However, a renderer for owned APIServices was merged 2026-09-17 (`:seedling: OPRUN-4723: registry+v1: add APIService renderer support (#2885)`, first in v1.12.0): it would generate an `APIService` named `<version>.<group>` (`groupPriorityMinimum: 2000`, `versionPriority: 15`, port default 443), a `ClusterRoleBinding` `<service>-system:auth-delegator` and a `RoleBinding` `<service>-auth-reader` in `kube-system`, with validator errors `owned apiservice %q has no deploymentName; a deployment is required to back the extension API server` / `owned apiservice %q references deployment %q which does not exist in the CSV install spec`. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go); [validators/validator.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/validators/validator.go)

**Dependencies, `olm.properties`, `olm.constraint`**
- Resolver rejects FBC bundles carrying `olm.package.required`, `olm.gvk.required` or `olm.constraint` properties with `bundle %q has a dependency declared via property %q which is currently not supported`. — [internal/operator-controller/resolve/validation.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/resolve/validation.go)
- `metadata/properties.yaml` IS read: its `properties` list is appended to the CSV annotation `olm.properties` ("copies properties from `metadata/propeties.yaml` ... into the CSV's `.metadata.annotations['olm.properties']` value, preserving any properties that are already present"); errors `failed to unmarshal csv.metadata.annotations['olm.properties']`, `failed to unmarshal metadata/properties.yaml`. `metadata/dependencies.yaml` is not referenced anywhere in operator-controller. — [rukpak/bundle/source/source.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/source/source.go); grep of `internal/`, `cmd/`, `api/` for `dependencies.yaml` (no hits)
- Nothing in operator-controller consumes `olm.properties` after it is copied, other than passing CSV annotations through as Helm chart metadata annotations (`chrt.Metadata.Annotations = rv1.CSV.GetAnnotations()`). — grep of `internal/` for `olm.properties` (only source.go); [applier/provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go)
- The resolver reads bundle version from the FBC `olm.package` property (`if p.Type == property.TypePackage`). — [internal/operator-controller/bundleutil/bundle.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/bundleutil/bundle.go)

**Upgrade edges: `replaces`/`skips`/`skipRange`, semver, `upgradeConstraintPolicy`**
- "OLM v1 supports legacy OLM semantics by default ... including `replaces`, `skips`, and `skipRange` directives ... If there are multiple possible successors ... In legacy OLM, the successor closest to the channel head is chosen. In OLM v1, the successor with the highest semantic version (semver) is chosen." "OLM v1 does not have a concept of a `replaces` chain. OLM v1 finds all entries that have a `replace`, `skip`, or `skipRange` value that covers the currently installed version." — [docs/concepts/upgrade-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/upgrade-support.md)
- `upgradeConstraintPolicy`: "`SelfCertified`: Does not limit the next version to the set of successors, and instead allows for any downgrade, sidegrade, or upgrade. `CatalogProvided`: Only allows the next version to come from the successors list. This is the default value." Field path `.spec.source.catalog.upgradeConstraintPolicy`. — [docs/concepts/upgrade-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/upgrade-support.md); [api/v1/clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)
- Code: `SuccessorsOf` = `legacySuccessor` OR the exact installed version; `legacySuccessor` checks, per channel entry, `Replaces == installedBundle.Name`, any `Skips == installedBundle.Name`, or `SkipRange` (parsed with `github.com/blang/semver/v4`, "OLM v0 used blang and there might still be registry+v1 bundles that rely on those specific differences") containing the installed version. — [internal/operator-controller/catalogmetadata/filter/successors.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/catalogmetadata/filter/successors.go)
- "Currently, OLM 1.0 does not support automatic upgrades to the next major version." Major-zero rules: no automatic patch upgrades when major and minor are `0` (`>= 0.0.1 <0.1.0`), no minor upgrades within major zero (`0.1.0` to `0.2.0`), but patch upgrades within `>= 0.1.0 <0.2.0` etc. are possible. — [docs/concepts/upgrade-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/upgrade-support.md)
- `spec.source.catalog.version` accepts comparison strings (`=`, `!=`, `>`, `<`, `>=`, `<=`), ranges (`">=3.0, <3.6"`), wildcards (`1.2.x`), tilde (`~1.2.3` = `>= 1.2.3, < 1.3.0`) and caret (`^1.2.3` = `>= 1.2.3, < 2.0.0`; `^0.2.3` = `>=0.2.3 <0.3.0`), joined with `||`. — [docs/concepts/version-ranges.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/version-ranges.md)
- Alpha gate `BundleReleaseSupport` (default false): "When disabled, release values are parsed from version build metadata (registry+v1 legacy)", e.g. `2` from `1.0.0+2`. — [features.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go); [internal/shared/labels/labels.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/labels/labels.go)

**`permissions` / `clusterPermissions` → RBAC bound to the deployment's ServiceAccount**
- One `ServiceAccount` is generated in the install namespace per distinct `serviceAccountName` found in `permissions` and `clusterPermissions`; an empty name means `default`, for which no object is generated. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- `permissions` → `Role` + `RoleBinding` in each target namespace, **except** in AllNamespaces mode: "If we're in AllNamespaces mode, promote the permissions to clusterPermissions", and "To keep parity with OLMv0, these will also include an extra rule to get, list, watch namespaces". `clusterPermissions` → `ClusterRole` + `ClusterRoleBinding`. Names are `<csvName>-<saName>` plus a deterministic hash suffix (`DefaultUniqueNameGenerator`), subject `ServiceAccount <saName>` in the install namespace. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go); [render.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/render.go)

**`spec.install.spec.deployments` → Deployments (what is preserved / injected)**
- "The generated resource aim to have parity with OLMv0 generated Deployment resources: `olm.targetNamespaces` annotation is set with the opts.TargetNamespace value; `olm.operatorNamespace` annotation is set with the opts.InstallNamespace value; the deployment spec's revision history limit is set to 1; merges csv annotations to the deployment template's annotations". Deployment labels come from the strategy spec's `label` field; name from `name`; namespace = install namespace. `olm.targetNamespaces` is `""` in AllNamespaces mode (join of `[""]`). — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- Deployment validators: `cluster service version contains duplicate strategy deployment spec '%s'`; `invalid cluster service version strategy deployment name '%s': ...` (DNS-1123 subdomain). — [validators/validator.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/validators/validator.go)
- Admin-side overrides of env/resources/volumes/etc. are NOT taken from the bundle; they come from `spec.config.inline.deploymentConfig` (OLM v0 `Subscription.spec.config` equivalent, alpha gate `DeploymentConfig`, default false): fields `nodeSelector`, `tolerations`, `resources`, `envFrom`, `env`, `volumes`, `volumeMounts`, `affinity`, `annotations`; "`selector` ... intentionally excluded". Merge semantics: env merged with deploymentConfig precedence; resources/nodeSelector replace; tolerations/volumes/volumeMounts/envFrom append; annotations merged with bundle precedence. Error when gate off: `unknown field "deploymentConfig"`. — [docs/draft/howto/customize-operator-deployments.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/customize-operator-deployments.md); [rukpak/bundle/README.md](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/README.md)

**CSV `metadata.annotations` handling**
- `operatorframework.io/suggested-namespace-template` (JSON `Namespace` object; PSA labels recommended) and `operatorframework.io/suggested-namespace` are consulted only "when the cluster admin does not provide an explicit `spec.namespace`, which requires the experimental feature set" (`BoxcutterRuntime` gate); fallback `<packageName>-system`; template takes priority. "In the standard feature set, `spec.namespace` is required, and the annotations described below are not consulted." "Do not change the resolved namespace name in a bundle upgrade." — [docs/draft/howto/namespace-configuration-for-authors.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/namespace-configuration-for-authors.md); [render/namespace.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/namespace.go)
- All CSV annotations are merged into every generated Deployment's pod-template annotations ("Add CSV annotations to template annotations", OLM v0 parity). — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- `olm.maxOpenShiftVersion` (inside `olm.properties`): documented in the OCP 4.18 and 4.19 OLM v1 Extensions guide ("authors can set the `olm.maxOpenShiftVersion` annotation to prevent administrators from updating the cluster before updating the installed Operator ... `"olm.properties": '[{"type": "olm.maxOpenShiftVersion", "value": "<cluster_version>"}]'`"); the same chapter in 4.20 and 4.21 no longer contains this text. — [OCP 4.19 Cluster extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.19/html/extensions/cluster-extensions) §5.3.5; absence verified by grep in the 4.20/4.21 pages

**OpenShift documentation of the same rules (verbatim)**
- 4.18: "The extension must use the registry+v1 bundle format introduced in OLM (Classic). The extension must support installation via the AllNamespaces install mode. The extension must not use webhooks. The extension must not declare dependencies by using any of the following file-based catalog properties: olm.gvk.required, olm.package.required, olm.constraint. OLM v1 checks that the extension you want to install meets these constraints. If the extension ... does not meet these constraints, an error message is printed in the cluster extension's conditions." — [OCP 4.18 Cluster extensions §5.1.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/extensions/cluster-extensions)
- 4.19: same list, plus "Support for the SingleNamespace and OwnNamespace install mode is included in OpenShift Container Platform 4.19 as a Technology Preview feature." and still "The extension must not use webhooks." — [OCP 4.19 Cluster extensions §5.1.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.19/html/extensions/cluster-extensions)

- Upstream main: "serviceAccount is a deprecated field and is completely ignored. - OpenShift 4.18–4.21 docs still require it: "spec.serviceAccount.name Specifies the name of the service account you created to install, update, and manage your extension." and "Because OpenShift Container Platform clusters use the OwnerReferencesPermissionEnforcement admission plugin, cluster extensions must have permissions to update the blockOwnerDeletion and ownerReferences finalizers." RBAC must cover: cluster roles/bindings for the controllers, "the resources defined in the CSV", "any cluster-scoped resources included in the bundle", CRDs. A "Preflight permissions check for cluster extensions (Technology Preview)" reports missing verbs in the status conditions. — [OCP 4.21 Cluster extensions §5.2.2.4, §5.2.3, §5.2.5](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/extensions/cluster-extensions)

### Inferences
- A WAO-style bundle must set `installModes: AllNamespaces: supported: true` to be installable on every OCP release 4.18–4.21 without a TechPreview feature set; declaring only `OwnNamespace` makes it uninstallable on 4.18 and TechPreview-only on 4.19–4.21.
- Because OLM v1 copies `spec.webhookdefinitions` fields verbatim, the "never change `failurePolicy`" constraint is preserved automatically; nothing in the renderer rewrites `failurePolicy`.
- Because `metadata/dependencies.yaml` is unread by operator-controller but `opm render`/FBC generation turns it into `olm.package.required`/`olm.gvk.required` properties, shipping a `dependencies.yaml` will cause a catalog-level rejection even though the bundle image itself loads. (Mapping of dependencies.yaml to FBC property names is not cited here — see Gaps.)
- `spec.minKubeVersion`, `spec.relatedImages`, `spec.replaces`, the CSV `olm.skipRange` annotation, `alm-examples`, `operators.openshift.io/*`, `features.operators.openshift.io/*`, `operatorframework.io/cluster-monitoring`, and `operators.operatorframework.io/builder` are not referenced anywhere in operator-controller's Go code (grep of `internal/`, `cmd/`, `api/`), so they are carried through only as inert Deployment pod-template annotations (for CSV annotations) or ignored entirely; upgrade edges come solely from FBC channel entries.
- Both webhook cert-provider gates default to `true` on main; the selection between cert-manager and Service CA at runtime is therefore a deployment decision of the distribution (OpenShift's cluster-olm-operator uses Service CA per the 4.21 docs).

### Gaps
- No primary source was found that states how `opm` maps `metadata/dependencies.yaml` entries (`olm.package`, `olm.gvk`) to the FBC `olm.package.required`/`olm.gvk.required` property names; the operator-bundle design doc only documents the dependencies.yaml side.
- I could not confirm which operator-controller version OCP 4.21's `cluster-olm-operator` vendors, so whether OCP 4.21/4.22 still enforces `spec.serviceAccount` at the API level (vs. the upstream v1.11.0+ "completely ignored" behavior) is unverified; the 4.21 docs still mandate it.
- Whether OCP 4.20+ honors `olm.maxOpenShiftVersion` for OLM v1-installed extensions is unverified (the text was removed from the 4.20/4.21 Extensions guide; no replacement statement was found).
- How the runtime chooses between `WebhookProviderCertManager` and `WebhookProviderOpenshiftServiceCA` when both are `true` was not traced in `cmd/operator-controller/main.go`.

## Q2. What does OLM v1 generate from a registry+v1 bundle, and which bundle kinds are allowed or rejected?

### Takeaway
The registry+v1 renderer runs 14 validators and 12 generators: it emits (Namespace in managed mode), ServiceAccounts, Roles/RoleBindings or promoted ClusterRoles/ClusterRoleBindings, CRDs, the bundle's "other" objects (only kinds in operator-registry's `supportedResources` map, namespaced ones forced into the install namespace), Deployments, Validating/MutatingWebhookConfigurations, Services for webhook deployments, (gated-off) APIServices, and cert-provider objects; everything is then applied as a Helm release (default) or a `ClusterObjectSet` (BoxcutterRuntime) carrying `olm.operatorframework.io/*` owner labels.

### Cited Findings

**Loading the bundle filesystem**
- `FromFS` reads `metadata/annotations.yaml` (package name taken from it), walks `manifests/` (error: `subdirectories are not allowed within the "manifests" directory of the bundle image filesystem: found %q`), parses every file with the kubectl resource builder (multi-document YAML allowed), classifies `ClusterServiceVersion` → `CSV`, `CustomResourceDefinition` → `CRDs`, everything else → `Others`; errors `no ClusterServiceVersion found in "manifests"` and `error parsing objects in %q: %v`; then merges `metadata/properties.yaml`. — [rukpak/bundle/source/source.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/source/source.go)

**Validators (all run, errors joined)**
- `CheckDeploymentSpecUniqueness`, `CheckDeploymentNameIsDNS1123SubDomain`, `CheckCRDResourceUniqueness` (`bundle contains duplicate custom resource definition '%s'`), `CheckOwnedCRDExistence` (`cluster service definition references owned custom resource definition '%s' not found in bundle`), `CheckPackageNameNotEmpty` (`package name is empty`), `CheckConversionWebhookSupport`, `CheckWebhookDeploymentReferentialIntegrity`, `CheckWebhookNameUniqueness`, `CheckWebhookNameIsDNS1123SubDomain`, `CheckConversionWebhookCRDReferenceUniqueness`, `CheckConversionWebhooksReferenceOwnedCRDs`, `CheckWebhookRules`, `CheckObjectSupport` (`unsupported resource %q with kind %q`), `CheckAPIServiceDeploymentReferentialIntegrity`. — [registryv1/registryv1.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/registryv1.go); [validators/validator.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/validators/validator.go)

**Generators (in order)**
- `BundleInstallNamespaceGenerator` (no-op when `spec.namespace` is set), `BundleCSVServiceAccountGenerator`, `BundleCSVPermissionsGenerator`, `BundleCSVClusterPermissionsGenerator`, `BundleCRDGenerator`, `BundleAdditionalResourcesGenerator`, `BundleCSVDeploymentGenerator`, `BundleValidatingWebhookResourceGenerator`, `BundleMutatingWebhookResourceGenerator`, `BundleDeploymentServiceResourceGenerator`, `BundleCSVAPIServiceGenerator`, `CertProviderResourceGenerator`. — [registryv1/registryv1.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/registryv1.go)
- "BundleAdditionalResourcesGenerator generates resources for the additional resources included in the bundle. If the bundle resource is namespace scoped, its namespace will be set to the value of opts.InstallNamespace." Error: `bundle contains unsupported resource: Name: %v, Kind: %v`. — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)
- The Service for a webhook deployment uses the deployment's `spec.selector.matchLabels` as the Service selector and one port per webhook (`port` = `containerPort` default 443, `targetPort` = webhook `targetPort` or the container port). — [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)

**Allowed "other object" kinds (operator-registry `supportedResources`, used by both `opm`/operator-sdk validation and operator-controller's `CheckObjectSupport`)**
- Namespaced (`true`): `ClusterServiceVersion`, `Service`, `ServiceAccount`, `Role`, `RoleBinding`, `PrometheusRule`, `ServiceMonitor`, `Secret`, `ConfigMap`, `PodDisruptionBudget`, `NetworkPolicy`, `PodMonitor`. Cluster-scoped (`false`): `CustomResourceDefinition`, `ClusterRole`, `ClusterRoleBinding`, `PriorityClass`, `VerticalPodAutoscaler`, `ConsoleYAMLSample`, `ConsoleQuickStart`, `ConsoleCLIDownload`, `ConsoleLink`, `ConsolePlugin`. `IsSupported(kind)` returns `(ok, namespaced)`. — [operator-registry pkg/lib/bundle/supported_resources.go](https://github.com/operator-framework/operator-registry/blob/master/pkg/lib/bundle/supported_resources.go)
- Hence rejected in `manifests/`: `Deployment`, `StatefulSet`, `DaemonSet`, `Namespace`, `Job`/`CronJob`, `Ingress`/`Route`, `ValidatingWebhookConfiguration`/`MutatingWebhookConfiguration`, `APIService`, `SecurityContextConstraints`, `OperatorGroup`/`Subscription`, and any custom-resource instance. — inference from the map above plus `CheckObjectSupport`

**Deployment / object labels OLM v1 adds (for the single-owner rule and for selection)**
- Objects and the Helm release/ClusterObjectSet are labelled with `olm.operatorframework.io/owner-kind: ClusterExtension`, `olm.operatorframework.io/owner-name: <ClusterExtension name>`, and storage labels `olm.operatorframework.io/package-name`, `olm.operatorframework.io/bundle-name`, `olm.operatorframework.io/bundle-version` (and `bundle-release`, `bundle-reference`, `revision-name`, `migrated-from-helm` in the Boxcutter path). — [internal/shared/labels/labels.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/labels/labels.go); [controllers/clusterextension_reconcile_steps.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/controllers/clusterextension_reconcile_steps.go)
- Example given upstream for selecting an extension's objects: `kubectl get deployment -n my-namespace -l olm.operatorframework.io/owner-name=my-operator -o yaml`. — [docs/draft/howto/customize-operator-deployments.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/customize-operator-deployments.md)

**How the rendered objects are applied**
- Default (Helm) applier: rendered objects become a synthetic Helm chart whose `Files` are the JSON objects and whose `Templates` are `{{.Files.Get "object-<hash>.json"}}` ("Some registry+v1 manifests may actually contain Go Template strings that are meant to survive ... we create the manifests as Files, and then template those files via simple Templates"); chart `Metadata.Annotations` = CSV annotations. — [applier/provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go)
- Boxcutter applier (alpha `BoxcutterRuntime` gate): first install uses `CollisionProtectionPrevent`; upgrades use `CollisionProtectionNone` "allow to adopt objects from previous release". `Prevent` "prevents owner collisions entirely by only allowing to work with objects itself has created"; `IfNoController` "allows to patch and override objects already present if they are not owned by another controller"; `None` "allows to patch and override objects already present and owned by other controllers. Be careful!". — [applier/boxcutter.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/boxcutter.go); [api/v1/clusterobjectset_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterobjectset_types.go)

### Inferences
- An OLM v0 bundle that ships standalone `Deployment`, `Namespace`, `OperatorGroup` or webhook-configuration manifests will fail `CheckObjectSupport`; the deployment must be expressed in `spec.install.spec.deployments` and webhooks in `spec.webhookdefinitions`.
- Any namespaced "other" object in `manifests/` (e.g. a `ConfigMap`, `ServiceMonitor`, `NetworkPolicy`) is forced into the install namespace regardless of the `metadata.namespace` it declares, so bundles must not rely on placing such objects elsewhere.
- Because every CSV annotation is merged into pod-template annotations, large annotations (e.g. `alm-examples`) inflate every pod template; this is OLM v0 parity, not a new constraint.

### Gaps
- The exact per-object behaviour when the Helm applier meets a pre-existing object was taken from Helm's own source (see Q3); operator-controller does not add its own wrapping message (grep of `applier/*.go` and `test/e2e` found no custom "already exists" strings).

## Q3. CRD rules across upgrades (preflight), and CRD/object ownership conflicts

### Takeaway
The CRD Upgrade Safety preflight (crdify-based, fail-closed on "unknown" changes) blocks scope changes, stored-version removal and a fixed list of schema-tightening changes; it is disabled only wholesale via `spec.install.preflight.crdUpgradeSafety.enforcement: None`; and OLM v1 enforces single ownership, so a CRD already present (from OLM v0 or another ClusterExtension) is never adopted — the Helm applier surfaces Helm's "exists and cannot be imported into the current release: invalid ownership metadata" error.

### Cited Findings

**Prohibited changes (upstream)**
- "The scope changes from Cluster to Namespace or from Namespace to Cluster; An existing stored version of the CRD is removed; A new required field is added to an existing version of the CRD; An existing field is removed from an existing version of the CRD; An existing field type is changed in an existing version of the CRD; A new default value is added to a field that did not previously have a default value; The default value of a field is changed; An existing default value of a field is removed; New enum restrictions are added to an existing field which did not previously have enum restrictions; Existing enum values from an existing field are removed; The minimum value of an existing field is increased in an existing version; The maximum value of an existing field is decreased in an existing version; Minimum or maximum field constraints are added to a field that did not previously have constraints." Rules apply to `minimum`, `minLength`, `minProperties`, `minItems`, `maximum`, `maxLength`, `maxProperties`, `maxItems`. "In cases where a change to the CRD does not fall into one of the disallowed change categories but is also unable to be properly detected as allowed, the CRD Upgrade Safety preflight check will prevent the upgrade and log an error for an 'unknown change.'" — [docs/concepts/crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md)
- Allowed: "Adding new enum values to the list of allowed enum values in a field; An existing required field is changed to optional in an existing version; The minimum value of an existing field is decreased in an existing version; The maximum value of an existing field is increased in an existing version; A new version of the CRD is added with no modifications to existing versions". — [docs/concepts/crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md)
- Example error outputs: `validating upgrade for CRD "test.example.com" failed: CustomResourceDefinition test.example.com failed upgrade safety validation. "NoScopeChange" validation failed: scope changed from "Namespaced" to "Cluster"` and `... "NoStoredVersionRemoved" validation failed: stored version "v1alpha1" removed`. — [docs/concepts/crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md)
- Implementation: uses `sigs.k8s.io/crdify` runner; default config `Conversion: ConversionPolicyIgnore` ("Ignore served version validations if conversion policy is set"), `UnhandledEnforcement: EnforcementPolicyError` ("Fail-closed by default"), `description` validation `EnforcementPolicyNone` ("OLM should not block on field description changes"), `enum` with `additionPolicy: Allow`. If the CRD does not yet exist on cluster the check is skipped ("if there is no existing CRD, there is nothing to break"). Error wrapper: `validating upgrade for CRD %q: ...`; per-property errors formatted `<version>: <property>: <check>: <msg>`; unhandled diffs summarised as `unhandled changes found (<field> <before> -> <after>; ...)`. — [internal/operator-controller/rukpak/preflights/crdupgradesafety/crdupgradesafety.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/preflights/crdupgradesafety/crdupgradesafety.go)

**Disabling**
- "`.spec.install.preflight.crdUpgradeSafety.enforcement` field with a value of `None`"; "You cannot disable individual field validators." API: "Allowed values are "None" or "Strict". The default value is "Strict"." CEL on `preflight`: `at least one of [crdUpgradeSafety] are required when preflight is specified`. — [docs/concepts/crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md); [api/v1/clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)
- OpenShift 4.21 adds: "If you disable the CRD upgrade safety preflight check in Operator Lifecycle Manager (OLM) v1, the Kubernetes API server still prevents the following operations: Changing scope from Cluster to Namespace or from Namespace to Cluster; Removing an existing stored version of the CRD" and classifies those two as "structural changes, which are handled by the Kubernetes API server". Field: "set the install.preflight.crdUpgradeSafety.enforcement field with the value of None". — [OCP 4.21 Cluster extensions §5.6](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/extensions/cluster-extensions)

**Single ownership / existing CRDs**
- "In OLM, **a Kubernetes resource can only be owned by a single `ClusterExtension` at a time**." "Operator bundles provide CustomResourceDefinitions (CRDs) ... This means a bundle can only be installed once in a cluster. Attempting to install another bundle that provides the same CRDs will result in a failure." "`ClusterExtensions` cannot share ownership of any resources ... (e.g., a `Deployment`, `CustomResourceDefinition`, or `Service`)". Example error: `CustomResourceDefinition 'logfilemetricexporters.logging.kubernetes.io' already exists in namespace 'kubernetes-logging' and cannot be managed by operator-controller`. — [docs/concepts/single-owner-objects.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/single-owner-objects.md)
- The Helm applier relies on Helm's install-time ownership validation, whose messages are: `%s exists and cannot be imported into the current release: %w` wrapping `invalid ownership metadata; ...` and `missing key %q: must be set to %q` for the label `app.kubernetes.io/managed-by` and annotations `meta.helm.sh/release-name`, `meta.helm.sh/release-namespace`. — [helm/helm pkg/action/validate.go](https://github.com/helm/helm/blob/main/pkg/action/validate.go)
- Webhook rules may not target `olm.operatorframework.io` or `*` groups, nor `admissionregistration.k8s.io` webhook configurations, "to reduce the blast radius of faulty webhooks and avoid deadlocks preventing the user from deleting OLMv1 resources". — [validators/validator.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/validators/validator.go)

### Inferences
- A CRD installed by OLM v0 (owned by a CSV, lacking Helm ownership metadata) blocks an OLM v1 install of a bundle that ships the same CRD; the OLM v0 operator must be removed (and the CRD either deleted or left unmanaged) before OLM v1 can own it. OLM v1 has no "adopt" option in the standard (Helm) runtime; adoption-like behaviour (`CollisionProtectionNone`) is used only between successive revisions of the same ClusterExtension in the alpha Boxcutter runtime.
- For the WAO PoC, every component CRD must be owned by exactly one ClusterExtension; a "parent" WAO bundle cannot re-ship CRDs that component bundles also ship.
- Upgrading a component across a CRD version that drops a stored version, changes defaults, or tightens validation requires either fixing the CRD or `enforcement: None` on the ClusterExtension; there is no per-field bypass.

### Gaps
- The upstream doc example error ("already exists in namespace ... and cannot be managed by operator-controller") was not located verbatim in the current code; the live message likely comes from Helm (quoted above) or from an older applier, so the exact string in a given release is unverified.
- Behaviour when the existing CRD is owned by OLM v0 was not found in docs as an explicit statement; it is inferred from the single-owner rule plus Helm's ownership validation.

## Q4. Alternatives to registry+v1 (Helm chart bundles, plain bundles) — state

### Takeaway
As of 2026-10-10, registry+v1 is the only bundle format operator-controller can load (there is no Helm or plain bundle source/loader in the code), although operator-registry's `opm alpha bundle` tooling already knows the `plain` and `helm` mediatype values and upstream docs list "Helm Chart and GitOps Support" as an aspiration; OpenShift 4.18–4.21 docs state registry+v1 is required.

(no implementation details). — [docs/index.md](https://github.com/operator-framework/operator-controller/blob/main/docs/index.md)
- The managed-namespaces design notes: "The behavior described in this document applies to the registry+v1 bundle format. - grep of operator-controller `internal/`, `cmd/`, `api/` for `helm+v3`, `plain+v0`, `olm.bundle.mediatype` or a Helm/plain bundle source returned no hits; the only `BundleSource` implementation is `fsBundleSource` for registry+v1, and `ClusterExtension.spec.source.sourceType` has "Catalog is currently the only implemented sourceType." — [rukpak/bundle/source/source.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/source/source.go); [api/v1/clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)

- Helm is used internally only as the *runtime* (rendered registry+v1 objects wrapped in a synthetic chart), and an alpha `BoxcutterRuntime` gate replaces Helm with `ClusterObjectSet` revisions. — [applier/provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go); [features.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go)

### Inferences
- Any plan to ship WAO as a Helm chart or "plain" bundle under OLM v1 has no supported path on OCP 4.18–4.21 or upstream v1.12.0; registry+v1 is the only option.

### Gaps
- No primary-source roadmap or RFC with a date for Helm-chart bundle support was found in the repository docs (the roadmap page is marked "Deprecated"); GitHub project boards were not fetched.

## Q5. Bundle image layout: `bundle.Dockerfile`, `metadata/annotations.yaml`, labels, `dependencies.yaml`, `properties.yaml`

### Takeaway
OLM v1 needs nothing beyond the standard OLM v0 bundle image: it reads `metadata/annotations.yaml` (only `operators.operatorframework.io.bundle.package.v1` is consumed), flat `manifests/` with exactly one CSV, and optional `metadata/properties.yaml`; image labels are used by catalog tooling, not by operator-controller.

### Cited Findings
- Standard layout and annotations (OLM v0 docs): `manifests/` (CSV + CRDs) and `metadata/annotations.yaml` with `operators.operatorframework.io.bundle.mediatype.v1: "registry+v1"`, `...bundle.manifests.v1: "manifests/"`, `...bundle.metadata.v1: "metadata/"`, `...bundle.package.v1: "<package>"`, `...bundle.channels.v1: "<channels>"`, `...bundle.channel.default.v1: "<channel>"`; `bundle.Dockerfile` is `FROM scratch` with the same keys as `LABEL`s and `ADD`s into `/manifests` and `/metadata/annotations.yaml`. Commands: `opm alpha bundle generate --directory ./etcd --package etcd --channels stable --default stable`, `podman build -t quay.io/namespace/bundle:latest -f bundle.Dockerfile .`, `opm alpha bundle validate --tag quay.io/test/test-operator:latest --image-builder docker`. — [olm.operatorframework.io creating-operator-bundle](https://olm.operatorframework.io/docs/tasks/creating-operator-bundle/)
- Label constants: `ManifestsLabel = "operators.operatorframework.io.bundle.manifests.v1"`, `MetadataLabel = "operators.operatorframework.io.bundle.metadata.v1"`, `MediatypeLabel = "operators.operatorframework.io.bundle.mediatype.v1"`, `PackageLabel = "operators.operatorframework.io.bundle.package.v1"`, `ChannelsLabel = "operators.operatorframework.io.bundle.channels.v1"`, `ChannelDefaultLabel = "operators.operatorframework.io.bundle.channel.default.v1"`, `AnnotationsFile = "annotations.yaml"`. — [operator-registry pkg/lib/bundle/generate.go](https://github.com/operator-framework/operator-registry/blob/master/pkg/lib/bundle/generate.go)
- `metadata/dependencies.yaml` format (OLM v0): "The dependency list will contain a `type` field for each item" with types `olm.package` (with semver `version` range, e.g. `">0.27.0"`) and `olm.gvk` (group/kind/version). "The documentation contains no `properties.yaml` specification." — [operator-registry docs/design/operator-bundle.md](https://github.com/operator-framework/operator-registry/blob/master/docs/design/operator-bundle.md)
- What operator-controller reads: `metadata/annotations.yaml` → `PackageName`; `manifests/` (no subdirectories, one CSV required); `metadata/properties.yaml` (`properties:` list, merged into `olm.properties`). The loader comment: "The filesystem is expected to conform to the registry+v1 format: metadata/annotations.yaml, metadata/properties.yaml, manifests/ ... manifests directory should not contain subdirectories". — [rukpak/bundle/source/source.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/source/source.go)
- Catalogs: the bundle must be reachable as a catalog entry with an `olm.package` property (version source) and channel entries (upgrade edges); OpenShift queries `olm.csv.metadata` to read install modes and `.spec.webhookdefinitions` from the rendered FBC. — [bundleutil/bundle.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/bundleutil/bundle.go); [OCP 4.21 Cluster extensions §5.2.1](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/extensions/cluster-extensions)

### Inferences
- OLM v1 adds no new required label or annotation (no `olm.bundle.mediatype` label is read from the image); an unchanged OLM v0 `bundle.Dockerfile` is sufficient provided `operators.operatorframework.io.bundle.package.v1` is present (it is the only annotation consumed, and `CheckPackageNameNotEmpty` fails otherwise).
- `metadata/dependencies.yaml` should be removed from a bundle targeting OLM v1 because, once rendered into an FBC, it yields the rejected `*.required` properties.
- `metadata/properties.yaml` is safe to keep (merged into `olm.properties`, then inert), but any `olm.constraint` placed there or in the CSV `olm.properties` annotation will be rejected if `opm` surfaces it as a bundle property in the catalog.

### Gaps
- Whether `opm render` surfaces `olm.constraint`/`olm.*.required` from `properties.yaml` into the FBC bundle properties (which is what the resolver checks) was not verified from opm source.

## Q6. Validation tooling for OLM v1 compatibility

### Takeaway
No tool ships an "OLM v1" validator suite; the closest is `operator-sdk bundle validate` with the `operatorframework` suite plus the OLM v1 runtime checks themselves (reported in `ClusterExtension.status.conditions`). `opm validate` validates FBC directories, `opm alpha bundle validate` validates a bundle image's format, and Red Hat `preflight check operator` runs certification checks (including `DeployableByOLM`, which exercises OLM v0).

### Cited Findings
- operator-sdk optional validators and their selector labels: `operatorhubv2` (`name=operatorhubv2`, `suite=operatorframework`), `capabilities` (`name=capabilities`, `suite=operatorframework`), `categories` (`name=categories`, `suite=operatorframework`), `operatorhub` (`name=operatorhub`, deprecated), `community` (`name=community`), `alpha-deprecated-apis` (`name=alpha-deprecated-apis`, `suite=operatorframework`), `good-practices` (`name=good-practices`, `suite=operatorframework`), `multiarch` (`name=multiarch`). — [operator-sdk internal/cmd/operator-sdk/bundle/validate/optional.go](https://github.com/operator-framework/operator-sdk/blob/master/internal/cmd/operator-sdk/bundle/validate/optional.go)
- Example commands from the CLI reference: `operator-sdk bundle validate ./bundle`; `operator-sdk bundle validate ./bundle --select-optional suite=operatorframework`; `operator-sdk bundle validate ./bundle --select-optional name=operatorhub --optional-values=k8s-version=1.22`; `operator-sdk bundle validate ./bundle --select-optional name=good-practices`; `operator-sdk bundle validate ./bundle --select-optional name=multiarch`; flags `--select-optional`, `--optional-values`, `--alpha-select-external`, `--list-optional`, `-o/--output text|json-alpha1`, `-b/--image-builder docker|podman|none`. — [operator-sdk CLI: operator-sdk bundle validate](https://sdk.operatorframework.io/docs/cli/operator-sdk_bundle_validate/)
- Default (always-run) validators: `ClusterServiceVersionValidator`, `CustomResourceDefinitionValidator`, `BundleValidator` (`DefaultBundleValidators`); the full set `AllValidators` adds `OperatorHubV2Validator`, `StandardCategoriesValidator`, `StandardCapabilitiesValidator`, `ObjectValidator` ("validates various custom objects in the bundle like PDBs and SCCs"), `OperatorGroupValidator`, `CommunityOperatorValidator`, `AlphaDeprecatedAPIsValidator`, `GoodPracticesValidator`, `MultipleArchitecturesValidator`. — [operator-framework/api pkg/validation/validation.go](https://github.com/operator-framework/api/blob/master/pkg/validation/validation.go)
- `opm alpha bundle validate` runs the operator-registry bundle validator; its "other object" check uses the same `supportedResources` list, and it has optional `operatorhub` and `bundle-objects` validations. — [operator-registry pkg/lib/bundle/validate.go](https://github.com/operator-framework/operator-registry/blob/master/pkg/lib/bundle/validate.go)
- `opm validate <directory>`: "Validate the declarative index config" / "Validate the declarative config JSON file(s) in a given directory" (FBC, not bundles). — [operator-registry cmd/opm/validate/validate.go](https://github.com/operator-framework/operator-registry/blob/master/cmd/opm/validate/validate.go)
- Red Hat preflight: `preflight check operator quay.io/example-namespace/example-operator:0.0.1`; "Some checks (like DeployableByOLM) require access to an OpenShift cluster through the current-context of the provided KUBECONFIG"; `PFLT_INDEXIMAGE` is used. Operator policy check names include `ValidateOperatorBundle`, `DeployableByOLM`, `RequiredAnnotations`, `AllImageRefsInRelatedImages` (policy files also exist for certified images, restricted-network awareness and SCC info). — [openshift-preflight README](https://github.com/redhat-openshift-ecosystem/openshift-preflight/blob/main/README.md); [internal/policy/operator](https://github.com/redhat-openshift-ecosystem/openshift-preflight/tree/main/internal/policy/operator)
- OLM v1's own runtime checks are the authoritative compatibility test: "OLM v1 verifies these criteria at install time and will surface violations in the `ClusterExtensions`'s `.status.conditions`"; config errors appear in the `Progressing` condition. — [docs/project/olmv1_limitations.md](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md); [docs/draft/howto/configure-bundles.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/configure-bundles.md)

### Inferences
- A practical pre-flight for OLM v1 is: (1) `operator-sdk bundle validate ./bundle --select-optional suite=operatorframework`; (2) `opm render <bundle-image> -o json | jq '... .value.spec.installModes'` and a `jq` check that `.spec.webhookdefinitions`, `.spec.apiservicedefinitions.owned` and properties `olm.*.required`/`olm.constraint` meet the Q1 rules; (3) a Kind/OpenShift install with `operator-controller` and reading `.status.conditions`.
- Red Hat `preflight`'s `DeployableByOLM` tests deployability under OLM v0 (it creates a `Subscription`/`OperatorGroup` flow), so passing it says nothing about OLM v1.

### Gaps
- No OLM v1-specific validator (`olmv1`, `name=olmv1`, etc.) exists in operator-sdk master or operator-framework/api master as of this check; nothing in the suite checks install modes vs. OLM v1 or the `*.required` properties.
- I did not fetch the full `preflight list-checks` output, so the operator check list above is partial (four named checks confirmed).

## Q7. Version/timeline matrix (which rule applies where)

### Takeaway
Webhooks: unsupported upstream before v1.3.0 (2025-05-22), GA gates since v1.6.0 (2025-11-11); on OCP unsupported in 4.18/4.19, Technology Preview in 4.20, supported in 4.21. Single/Own namespace: alpha upstream since v1.2.0 (2025-03-04) and still alpha on main; Technology Preview on OCP 4.19–4.21 (4.21 requires `TechPreviewNoUpgrade`). APIService: unsupported everywhere. `spec.serviceAccount`: required on OCP 4.18–4.21 docs; ignored upstream since v1.11.0 (2026-07-23).

### Cited Findings
- Upstream commit → first tag mapping (git): Single/Own namespace `df35dcd` 2025-02-27 → v1.2.0; webhooks `966241f` 2025-05-14 and service-ca provider `8f2f1e9` 2025-05-15 → v1.3.0; webhook gates GA `6b88f77` 2025-10-20 → v1.6.0; Single/Own GA attempt `3c2fcb4` 2025-10-27 and revert `760855f` 2025-10-29 → v1.6.0; `serviceAccount` deprecation `1bbe788` 2026-07-20 → v1.11.0; APIService renderer `c53476c` 2026-09-17 → v1.12.0 (still gated off in provider). — operator-controller git history (`git log -S`, `git tag --contains`), see file links above
- Feature-gate table on main: `SingleOwnNamespaceInstallSupport` alpha/false; `WebhookProviderCertManager` GA/true; `WebhookProviderOpenshiftServiceCA` GA/true; `BoxcutterRuntime` alpha/false; `DeploymentConfig` alpha/false; `BundleReleaseSupport` alpha/false. — [features.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go)
- OCP 4.18: AllNamespaces required, "must not use webhooks", no Single/Own mention, `spec.serviceAccount` required. — [OCP 4.18](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/extensions/cluster-extensions)
- OCP 4.19: Single/Own "Technology Preview", webhooks "must not use", "Preflight permissions check for cluster extensions (Technology Preview)". — [OCP 4.19](https://docs.redhat.com/en/documentation/openshift_container_platform/4.19/html/extensions/cluster-extensions)
- OCP 4.20: Single/Own TP, webhooks TP: "Deploying an extension in a specific namespace and installing an extension with webhooks is a Technology Preview feature only." — [OCP 4.20](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions)
- OCP 4.21: webhooks supported (Service CA), watch namespace TP requiring `TechPreviewNoUpgrade`, `spec.serviceAccount.name` still documented as required in the install procedure, CRD upgrade safety as in Q3. — [OCP 4.21](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/extensions/cluster-extensions)

### Inferences
- A bundle written to the strictest rule set (AllNamespaces supported, no `*.required`/`olm.constraint`, no APIService, webhooks only if targeting OCP ≥ 4.21 or upstream ≥ v1.3.0, serving certs read from `/tmp/k8s-webhook-server/serving-certs`, only allowed "other" kinds, flat `manifests/`, one CSV, DNS-1123 deployment/webhook names) installs on every listed version.

### Gaps
- OCP release-to-operator-controller version mapping (which upstream tag each OCP minor vendors) was not found in primary docs.
