# OLM v1 architecture and core APIs (operator-controller + catalogd), upstream and OpenShift, as of 2026-10-10

Research method note: Red Hat's `html-single` pages and the GitHub releases page were fetched raw (curl / unauthenticated GitHub API / shallow git clone of `operator-framework/operator-controller` at commit `8ab554bd` dated 2026-10-09 and of `openshift/operator-framework-operator-controller` at `b94acf3d` dated 2026-09-28) and grepped, because summarised fetches of the same pages returned only tables of contents and, in one case, wrong release dates. Every date and field name below was read from the raw source. Where upstream `main` and the OCP 4.21 docs disagree, both are recorded with their version.

## Key question 1: Components, API versions, and the exact ClusterExtension / ClusterCatalog APIs

### Takeaway
OLM v1 is two controllers in one repo, `operator-controller` and `catalogd`, exposing three cluster-scoped CRDs in API group `olm.operatorframework.io/v1`: `ClusterExtension`, `ClusterCatalog`, and (experimental/Tech Preview only) a revision CRD that OCP 4.21 ships as `ClusterExtensionRevision` and upstream v1.9.0+ renamed to `ClusterObjectSet`. The `v1alpha1` versions were replaced by `v1` in operator-controller v1.0.0-rc1 (2024-11-12); OCP has only ever documented `olm.operatorframework.io/v1` from the 4.18 GA onward.

### Cited Findings

Components
- Upstream architecture doc: "OLM v1 ... consists of two primary components: 1. operator-controller 2. catalogD". operator-controller responsibilities: "Managing a cache of catalog metadata provided by catalogD through its HTTP server", "Identifying the appropriate `registry+v1` bundle that meets the constraints defined in the `ClusterExtension` resource (e.g., package name, version, channel)", "Unpacking and applying bundle manifests". Sub-components: Cluster Extension Controller, Resolver, Bundle Cache. catalogd sub-components: ClusterCatalog Controller, CatalogD HTTP Server, CatalogD Content Cache. — [Source](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_architecture.md)
- The separate `operator-framework/catalogd` repository is archived (`archived: true`, last push 2025-03-03); catalogd was merged into operator-controller in release v1.2.0 ("[Monorepo] PHASE 1 - Add Catalogd to Operator-Controller Repository", PR #1542). — [Source](https://github.com/operator-framework/catalogd); [Source](https://github.com/operator-framework/operator-controller/releases/tag/v1.2.0)
- OCP 4.21 doc: "Operator Lifecycle Manager (OLM) v1 uses two key microservice components, Operator Controller and Catalogd, to unpack content and manage extensions on your cluster. Operator Controller: Extends Kubernetes with an API to install and manage Operators and extensions using metadata from Catalogd. Catalogd: Unpacks file-based catalog (FBC) content and hosts metadata so users can discover installable extensions." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- OCP 4.21 doc: "This API is provided as clusterextension.olm.operatorframework.io by the new Operator Controller component." and "Earlier Technology Preview phases of OLM v1 introduced a new Operator API; this API is renamed ClusterExtension in OpenShift Container Platform 4.16". — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)

### Inferences
- OCP 4.21 (API index lists `ClusterExtensionRevision`) must be built from an upstream level between v1.6.0 (Boxcutter introduced, 2025-11-11) and before v1.9.0 (rename to `ClusterObjectSet`, 2026-06-08). The exact upstream tag per OCP minor was not found in a primary source.
- Because `spec.serviceAccount` is deprecated-and-ignored on upstream main but still documented as the installation mechanism in OCP 4.21, an operator author targeting OpenShift today must still ship/document an installer ServiceAccount and RBAC; the field remains schema-valid upstream so manifests carrying it will not be rejected after the deprecation.

## Key question 2: Resolution rules — one bundle, semver range syntax, channel filtering, catalog priority, label selectors; upgrade semantics

### Takeaway
Resolution picks exactly one bundle: the highest semver that satisfies `packageName` AND `version` range AND `channels`, restricted to catalogs matched by `selector`, with ties broken by `ClusterCatalog.spec.priority`, deprecated bundles deprioritised, and an error if ambiguity remains. Upgrades follow catalog `replaces`/`skips`/`skipRange` edges under `CatalogProvided`, choosing the highest-semver successor rather than OLM v0's closest-to-channel-head.

### Cited Findings
- Version syntax (upstream Go doc, verbatim): operators `=`, `!=`, `<`, `>`, `>=`, `<=`; wildcards "`1.2.x`, `1.2.X`, and `1.2.*` is equivalent to `>=1.2.0, < 1.3.0`", "`<= 2.x` ... equivalent to `< 3`", "`x`, `X`, and `*` is equivalent to `>= 0.0.0`"; tilde "`~1.2.3` is equivalent to `>=1.2.3, <1.3.0`", "`~1` and `~1.x` is equivalent to `>=1, <2`", "`~2.3` is equivalent to `>=2.3, <2.4`"; caret "`^1.2.3` is equivalent to `>=1.2.3, <2.0.0`", "`^0.2.3` is equivalent to `>=0.2.3, <0.3.0`", "`^0.0.3` is equvalent to `>=0.0.3, <0.0.4`", "`^0` is equivalent to `>=0.0.0, <1.0.0`"; OR "`>=1.2.3, <2.0.0 || >3.0.0`", "`^0 || ^3 || ^5`". "Acceptable version ranges are no longer than 64 characters." Pinned example: "`0.6.0`, which means \"only install version 0.6.0 and never upgrade from this version\"". — [Source](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go); same table rendered at [Source](https://operator-framework.github.io/operator-controller/concepts/version-ranges/)
- OCP 4.21 doc: "A comparison string is a list of space- or comma-separated values and one or more comparison operators enclosed in double quotation marks (\"). You can add another comparison string by including an OR, or double vertical bar (||), comparison operator between the strings." and "OLM v1 installs or updates to the latest version that can be resolved within the specified range ... An update is not installed if it is outside of the specified range or if it cannot be resolved successfully." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Channel AND version: "Given channel is set to \"foo\"; Given version is set to \">=1.0.0, <1.5.0\"; Only bundles that exist in channel \"foo\" AND satisfy the version range comparison are considered installable; Automatic upgrades are constrained to upgrade edges defined by the selected channel." — [Source](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)
- Catalog selection: selectors use `spec.source.catalog.selector.matchLabels` / `matchExpressions` (operators `In`, `NotIn`, `DoesNotExist`); "The system automatically applies `olm.operatorframework.io/metadata.name` labels to ClusterCatalogs"; resolution order: "1. Priority-based selection ... 2. Deprecated bundles are deprioritized. If non-deprecated bundles are available, deprecated ones are ignored 3. If multiple bundles are from catalogs with the same highest priority, and there is still ambiguity, an error is generated". — [Source](https://operator-framework.github.io/operator-controller/concepts/controlling-catalog-selection/)
- OCP 4.21 example selecting a Red Hat catalog by its auto-label:
  ```yaml
  apiVersion: olm.operatorframework.io/v1
  kind: ClusterExtension
  metadata:
    name: <example_extension>
  spec:
    namespace: <example_namespace>
    serviceAccount:
      name: <example_extension>-installer
    source:
      sourceType: Catalog
      catalog:
        packageName: <example_extension>-operator
        selector:
          matchLabels:
            olm.operatorframework.io/metadata.name: openshift-redhat-operators
  ```
  and "If you use both the matchLabels and matchExpressions fields, the selected catalog must satisfy all specified criteria." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Upgrade edges: "OLM v1 supports OLM (Classic) semantics for update paths ... Support includes replaces, skips, and skipRange directives, with a few noted differences ... In OLM (Classic), the successor closest to the channel head is chosen. In OLM v1, the successor with the highest semantic version (semver) is chosen." and "OLM v1 does not have a concept of a replaces chain. OLM v1 finds all entries that have a replace, skip, or skipRange value that covers the currently installed version." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index); same text upstream at [Source](https://operator-framework.github.io/operator-controller/concepts/upgrade-support/)
- Major versions / rollback: "OLM v1 does not support automatic updates to the next major version or rollbacks to an earlier version. If you want to perform a major version update or rollback, you must verify and force the update manually" by setting `upgradeConstraintPolicy: SelfCertified`. — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Upstream removed the `ForceSemverUpgradeConstraints` feature gate in v1.2.0 ("remove ForceSemverUpgradeConstraints feature gate and implementation (#1638)"), so catalog edges are the only automatic-upgrade mechanism. — [Source](https://github.com/operator-framework/operator-controller/releases/tag/v1.2.0)
- Bundle `release` tie-break (experimental): "When multiple releases exist for the same version, higher releases are preferred. An unset release is less preferred than all other release values." Gate `BundleReleaseSupport` (Alpha, default false). — [Source](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go); [Source](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/features/features.go)
- Red Hat default catalog priorities (OCP 4.21): `openshift-redhat-operators` `priority: -100`, `openshift-certified-operators` `priority: -200`, `openshift-redhat-marketplace` `priority: -300`, `openshift-community-operators` `priority: -400`; refs `registry.redhat.io/redhat/redhat-operator-index:v4.21`, `.../certified-operator-index:v4.21`, `.../redhat-marketplace-index:v4.21`, `.../community-operator-index:v4.21`, each with `pollIntervalMinutes: 10`. — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)

### Inferences
- Because default Red Hat catalogs carry negative priorities, any user-created `ClusterCatalog` left at the default `priority: 0` outranks all four Red Hat catalogs for a package present in both; authors shipping their own catalog should pin with `selector` rather than rely on priority.

### Gaps
- No primary statement was found on how the resolver behaves when the selected catalog becomes `Unavailable` mid-life, beyond the downstream e2e title "ClusterExtension behavior after selected catalog removal should keep Installed=True and report Progressing=True/Retrying when the selected catalog is removed" ([Source](https://github.com/openshift/operator-framework-operator-controller/blob/main/openshift/tests-extension/cmd/main.go)).

## Key question 3: How OLM v1 differs conceptually from OLM v0 (Classic)

### Takeaway
OLM v1 replaces Subscription/CSV/OperatorGroup/InstallPlan with one cluster-scoped `ClusterExtension`, treats every extension as a cluster-wide singleton with single ownership of every managed object, does constraint checking only (no automatic dependency installation), reconciles continuously instead of one-shot InstallPlans, and (upstream) now runs as cluster-admin with the deprecated per-extension ServiceAccount model being phased out.

### Cited Findings
- Design decisions (upstream): "multi-tenancy promises that OLMv0 made were false promises"; OLM v1 "will not" provide first-class watched-namespace configuration, assumes "a controller WILL reconcile an object no matter where it is in the cluster"; "Creating or modifying a ClusterExtension triggers cluster-admin-level operations"; "OLM v1 performs validation but does not automatically resolve or install dependencies"; bundles may be "arbitrary Kubernetes objects while maintaining special handling for CRDs, controllers, webhooks, and RBAC"; GitOps-friendly: "Users can pin versions, pause management, and delete all managed content by deleting the OLM object." — [Source](https://operator-framework.github.io/operator-controller/project/olmv1_design_decisions/)
- OCP 4.18 release note: "OLM v1 enhances reliability through continuous reconciliation. Rather than relying on single attempts, OLM v1 proactively addresses Operator installation and update failures, automatically retrying until the issue is resolved. This eliminates the manual steps previously required, such as deleting InstallPlan API objects". Also: "treating Operators, which consist of custom controllers and CRDs, as cluster-wide singletons." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html-single/release_notes/index)
- OCP 4.21: "Cluster prefix clearly indicates that ClusterExtension objects are cluster-scoped, a change from OLM (Classic) where Operators could be either namespace-scoped or cluster-scoped." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Single ownership: "a Kubernetes resource can only be owned by a single `ClusterExtension` at a time ... Operator Bundles That Provide a CRD Can Only Be Installed Once ... `ClusterExtensions` Cannot Share Objects". Example error: `CustomResourceDefinition 'logfilemetricexporters.logging.kubernetes.io' already exists in namespace 'kubernetes-logging' and cannot be managed by operator-controller`. — [Source](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/single-owner-objects.md); OCP mirror text at [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Configuration shift table (upstream draft): "Namespace Scope — OLM v0: Defined by OperatorGroup ... OLM v1: You provide a `watchNamespace` value directly in the `ClusterExtension` YAML. User Settings — OLM v0: `Subscription.spec.config` ... OLM v1: `ClusterExtension.spec.config.inline`. Multi-Tenancy — OLM v0: 'Install Modes' allowed multiple instances ... OLM v1: 'Install Modes' are treated as bundle configuration. You install the extension once". — [Source](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/configure-bundles.md)
- Content constraints (upstream limitations page): "OLM v1 only supports installing operators packaged in OLM v0 bundles, also known as `registry+v1` bundles"; must support `AllNamespaces` ("OLM v1 supports `SingleNamespace` and `OwnNamespace` modes for `registry+v1` bundles for backwards compatibility with OLM v0, but these are not recommended"); "must not declare dependencies using ... `olm.gvk.required`, `olm.package.required`, `olm.constraint`"; "must not define `APIService`s in the `ClusterServiceVersion`"; "OLM v1 does not support the `OperatorConditions` API introduced in legacy OLM." — [Source](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)
- Service-account model, OCP 4.21 (still current there): "OLM v1 prioritizes security by minimizing its permission requirements ... By using user-provided ServiceAccount objects for Operator lifecycle operations" (4.18 RN) and the 4.21 required-permissions list: installer SA must be able to manage "Cluster role and cluster role bindings for the controllers", "Custom resource definitions", "Deployments", "Extension permissions ... defined in the CSV", "Roles and role bindings", "Service accounts", plus "Because OpenShift Container Platform clusters use the OwnerReferencesPermissionEnforcement admission plugin, cluster extensions must have permissions to update the blockOwnerDeletion and ownerReferences finalizers." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html-single/release_notes/index); [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)
- Service-account model, upstream direction: OpenShift enhancement `service-account-deprecation` (created 2025-10-08, updated 2026-06-19, status `implementable`, tracking OCPSTRAT-3040): "Deprecate the `spec.serviceAccount` field from the `ClusterExtension` API in the operator-controller and grant the controller cluster-admin privileges ... Access control shifts from per-extension ServiceAccount RBAC to standard Kubernetes RBAC on who can create `ClusterExtension` resources. A ValidatingAdmissionPolicy is used to emit deprecation warnings when the field is set." — [Source](https://github.com/openshift/enhancements/blob/master/enhancements/olm/service-account-deprecation.md)
- "Catalog-driven": `ClusterCatalog` "makes File-Based Catalog (FBC) data available to your cluster"; the only `sourceType` for a ClusterExtension is `Catalog`, and catalogd "serves catalog information to clients, such as the Cluster Extension Controller". — [Source](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clustercatalog_types.go); [Source](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_architecture.md)
- OCP 4.21 glossary still defines OLM v0 terms (Cluster service version, Install plan, Operator group, Subscription) for context, and the single-ownership section states "OLM v1 does not support multi-tenancy. You cannot install the same extension more than once on a cluster. As a result, the MultiNamespace install mode is not supported." — [Source](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)

### Inferences
- "No catalog-less/direct image install": the `sourceType` enum contains only `Catalog` on upstream main and in all OCP docs; the deprecated upstream roadmap item "F18 - Standalone extension bundle installation" ([Source](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_roadmap.md)) is not implemented in the API.

### Gaps
- No primary source found stating whether OCP has shipped (or when it will ship) the upstream serviceAccount deprecation; OCP 4.21 docs are unambiguous that the SA is still required there.

## Key question 4: Status conditions and reasons; diagnosing a failed install or upgrade

### Takeaway
`ClusterExtension` exposes `Installed` and `Progressing` plus the deprecation rollup `Deprecated` with `PackageDeprecated`, `ChannelDeprecated`, `BundleDeprecated`; the reason set is `Succeeded`, `Failed`, `Retrying`, `Blocked`, `Absent`, `RollingOut`, `InvalidConfiguration`, `ProgressDeadlineExceeded`, `ProbesSucceeded`, `Deprecated`/`NotDeprecated`/`DeprecationStatusUnknown`. ## Key question 5: The installer — Helm-based applier, Boxcutter/ClusterObjectSet, registry+v1 conversion, ownership labels

### Takeaway
The standard (GA) path converts a `registry+v1` bundle (CSV + CRDs + extra manifests) into plain Kubernetes objects via an internal renderer, wraps them in a generated Helm chart and applies them with the Helm SDK; the experimental `BoxcutterRuntime` path instead snapshots the rendered objects into an immutable `ClusterObjectSet` (formerly `ClusterExtensionRevision`) revision applied in 13 ordered phases with readiness probes. Objects carry `olm.operatorframework.io/owner-kind`, `owner-name`, `package-name`, `bundle-name`, `bundle-version` labels.

### Cited Findings

## Key question 7: Upstream release timeline and roadmap state in 2026

### Takeaway
Upstream shipped v1.6.0 through v1.12.0 between 2025-11-11 and 2026-09-24, adding Boxcutter revisions, webhook GA, the config API, DeploymentConfig, managed namespaces and the serviceAccount deprecation, while removing native Helm-chart support; the formal roadmap document is marked deprecated in favour of the GitHub project board.
