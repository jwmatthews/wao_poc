# Developer workflow for building and testing an operator against OLM v1 (operator-controller + catalogd), kind and OpenShift, as of 2026-10-10

Scope note: all upstream facts below were taken from the `operator-framework/operator-controller` repository at commit `8ab554bd18748cc1941593e00806dfef7892acb2` (2026-10-09) and the GitHub Releases API, the `openshift/openshift-docs` branches `enterprise-4.20` and `enterprise-4.22`, `openshift/cluster-olm-operator` (commit `cd7988325274f81aba1f7264fb67649a45a8369a`, 2026-09-28) and `openshift/api` `master`. Commands marked "upstream" apply to the kind/`olmv1-system` install; commands marked "OpenShift" apply to `openshift-operator-controller`/`openshift-catalogd`.

## Key question 1: Installing OLM v1 upstream on kind (install command, what it installs, versions, feature gates)

### Takeaway
As of 2026-10-10 the latest release is operator-controller v1.12.0 (2026-09-24); `install.sh` installs cert-manager v1.18.2 if absent, then applies a single `operator-controller.yaml` manifest into `olmv1-system` (deployments `catalogd-controller-manager` and `operator-controller-controller-manager`), and optionally the `operatorhubio` ClusterCatalog. The current feature-gate set is `SingleOwnNamespaceInstallSupport`, `WebhookProviderCertManager`, `WebhookProviderOpenshiftServiceCA`, `BoxcutterRuntime`, `DeploymentConfig`, `BundleReleaseSupport` (operator-controller) plus `APIV1MetasHandler`, `GraphQLCatalogQueries` (catalogd); `PreflightPermissions`, `SyntheticPermissions` and `HelmChartSupport` no longer exist, and `spec.serviceAccount` is deprecated and ignored because operator-controller now runs as cluster-admin.

### Inferences
- Since `install.sh` skips cert-manager only when all three of the CRD and both deployments exist, a cluster with a Helm-installed cert-manager in a different namespace will get a second cert-manager applied; pre-create or install into `cert-manager` namespace first if you must coexist.
- The `WebhookProviderCertManager=true` default plus the bundled cert-manager means webhook-bearing bundles install on kind with no extra setup; on OpenShift `cluster-olm-operator` forces `WebhookProviderCertManager=false` and uses Service CA.
- The `--global-pull-secret=openshift-config/pull-secret` flag is only emitted for the OpenShift Helm profile; upstream users wanting a global pull secret must add the flag themselves (e.g. `extraArguments` or `kubectl set args`), and the referenced secret must exist in the named namespace.

## Key question 2: Loading local images into kind; how catalogd/operator-controller pull bundle and catalog images; insecure/private registries

### Takeaway
catalogd and operator-controller pull catalog and bundle images themselves with the containers/image library (`go.podman.io/image/v5`), honoring `--pull-cas-dir` for CA trust and `--global-pull-secret` for auth; the project's own extension-developer e2e therefore deploys an in-cluster TLS registry (`docker-registry.operator-controller-e2e.svc:5000`, certificate issued by cert-manager) and pushes bundle and catalog images into it with `crane` over a port-forward instead of using `kind load`.

### Cited Findings
- operator-controller builds the image `SystemContext` from its flags: `DockerCertPath: cfg.pullCasDir`, `OCICertPath: cfg.pullCasDir`, and `srcContext.AuthFilePath = authFilePath` where the auth file is materialized from the `--global-pull-secret` secret — [cmd/operator-controller/main.go](https://github.com/operator-framework/operator-controller/blob/main/cmd/operator-controller/main.go)
- The puller is `ContainersImagePuller` using `go.podman.io/image/v5` (`sysregistriesv2` imported); if no signature policy is found it logs `no default policy found, using insecure policy` and uses `{"default":[{"type":"insecureAcceptAnything"}]}` — [internal/shared/util/image/pull.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/util/image/pull.go)
- Bundle unpack cache lives at `filepath.Join(cfg.cachePath, "unpack")` under `--cache-path` (default `/var/cache/operator-controller`); catalogd's at `filepath.Join(cfg.cacheDir, "unpack")` under `--cache-dir` (default `/var/cache/catalogd`) — [cmd/operator-controller/main.go](https://github.com/operator-framework/operator-controller/blob/main/cmd/operator-controller/main.go), [cmd/catalogd/main.go](https://github.com/operator-framework/operator-controller/blob/main/cmd/catalogd/main.go)
- Image cache behaviour: when content for a canonical ref is already present the puller logs `image already unpacked` and skips the pull; otherwise `unpacking image` into a read-only directory — [internal/shared/util/image/cache.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/util/image/cache.go)
- v1.4.0 added "Support serviceaccount pull secrets" — [v1.4.0 release](https://github.com/operator-framework/operator-controller/releases/tag/v1.4.0)
- The e2e in-cluster registry: `export CLUSTER_REGISTRY_HOST := docker-registry.operator-controller-e2e.svc:5000` — [Makefile](https://github.com/operator-framework/operator-controller/blob/main/Makefile); the registry helper applies namespace `operator-controller-e2e`, a cert-manager `Certificate` with `IsCA(true)`, DNS names `<name>.<namespace>.svc` and `<name>.<namespace>.svc.cluster.local`, issuer `olmv1-ca`, then a Deployment and Service, all via server-side apply ("idempotent") — [test/internal/registry/registry.go](https://github.com/operator-framework/operator-controller/blob/main/test/internal/registry/registry.go)
- The extension-developer e2e builds the operator with operator-sdk (`operator-sdk init --domain=oc-opdev-e2e.operatorframework.io`, `operator-sdk create api --group=... --version v1alpha1 --kind Registry --resource --controller`, `make generate manifests`, `make docker-build IMG=...`, `make bundle IMG=... VERSION=0.0.1`, `make bundle-build BUNDLE_IMG="${cluster_registry_host}/bundles/registry-v1/registry-bundle:v0.0.1"`), writes a hand-made FBC `catalog/index.yaml` with `olm.package`, `olm.bundle` (with `"image": "${reg_bundle_img}"` and an `olm.package` property `{"packageName": ..., "version": "0.0.1"}`) and `olm.channel` `preview`, and builds it with a Dockerfile `FROM scratch` / `ADD catalog /configs` / `LABEL operators.operatorframework.io.index.configs.v1=/configs` via `${container_tool} build --provenance=false ...`; the comment says "Images are built and tagged locally; pushing to the registry is handled by the Go test code via crane + port-forward." and "Push is handled by the Go test via crane + port-forward, because docker push goes through the Docker daemon which may be in a different network context (e.g. colima VM)." — [test/extension-developer-e2e/setup.sh](https://github.com/operator-framework/operator-controller/blob/main/test/extension-developer-e2e/setup.sh)

- OpenShift pulls use the cluster global pull secret: `--global-pull-secret=openshift-config/pull-secret` on both operator-controller and catalogd deployments in the OpenShift Helm profile — [operator-controller deployment template](https://github.com/operator-framework/operator-controller/blob/main/helm/olmv1/templates/deployment-olmv1-system-operator-controller-controller-manager.yml), [catalogd deployment template](https://github.com/operator-framework/operator-controller/blob/main/helm/olmv1/templates/deployment-olmv1-system-catalogd-controller-manager.yml)

### Inferences
- Because the controllers pull with containers/image inside their own pods, `kind load docker-image` (which seeds containerd on the nodes) does not make a bundle or catalog image visible to catalogd/operator-controller; images must be served by a registry reachable from inside the pods (in-cluster registry, host registry reachable via `host.docker.internal`/node IP, or a public registry). This matches why the project's own e2e uses an in-cluster registry plus `crane` push rather than `kind load`.
- Trusting a self-signed in-cluster registry on kind requires mounting its CA into `/var/ca-certs` (what the standard install already does via `--pull-cas-dir=/var/ca-certs` when `certManager.enabled`) or issuing the registry certificate from the same `olmv1-ca` cert-manager issuer as the e2e helper does.
- The `--pull-cas-dir` watcher in operator-controller calls `os.Exit` on CA directory changes, so updating the CA bundle restarts the pod; expect a brief restart after rotating CAs (from the `main.go` summary).
- No flag was found that marks a registry as plain-HTTP/insecure; the only evidence is the imported `sysregistriesv2` package, which reads `registries.conf`. Whether a mounted `registries.conf` with `insecure = true` is honored was not verified (see Gaps).

### Gaps
- No primary documentation describing a supported way to use plain-HTTP (non-TLS) registries with catalogd/operator-controller was found; the dedicated how-to URL (`draft/howto/private-registries/`) returned 404.
- The exact behaviour of `crane.Insecure` + port-forward on macOS/Podman beyond the comment in `setup.sh` was not validated.

## Key question 4: Testing upgrades, forcing re-resolution, downgrades, CRD upgrade safety

### Takeaway
Publish v2 by adding an `olm.bundle` and channel entry to the FBC and rebuilding the catalog image; catalogd re-unpacks on `pollIntervalMinutes` (tag refs only), on spec change, or when its cache is missing, and operator-controller resolves the highest semver successor under `upgradeConstraintPolicy: CatalogProvided` (default), or any version under `SelfCertified`; CRD upgrade safety failures surface as `validating upgrade for CRD "<name>" failed: CustomResourceDefinition <name> failed upgrade safety validation. "<Validator>" validation failed: ...` and can be disabled with `install.preflight.crdUpgradeSafety.enforcement: None`.

### Cited Findings
- Upgrade by edit or patch: `kubectl patch clusterextension argocd --type='merge' -p '{"spec": {"source": {"catalog": {"version": "0.2.1"}}}}'`; prerequisites include "Users cannot upgrade between minor versions with major version zero"; note that `kubectl.kubernetes.io/last-applied-configuration` differs between apply and patch — [tutorials/upgrade-extension.md](https://github.com/operator-framework/operator-controller/blob/main/docs/tutorials/upgrade-extension.md)
- Upgrade semantics: "In OLM v1, the successor with the highest semantic version (semver) is chosen"; "OLM v1 finds all entries that have a `replace`, `skip`, or `skipRange` value that covers the currently installed version"; `SelfCertified` "allows for any downgrade, sidegrade, or upgrade"; `CatalogProvided` "Only allows the next version to come from the successors list. This is the default value."; "OLM 1.0 does not support automatic upgrades to the next major version"; within major 0, "You cannot automatically upgrade from one patch version to another when both major and minor versions are `0`" and "cannot automatically upgrade from one minor version to another minor version within the major version zero" — [concepts/upgrade-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/upgrade-support.md)
- Downgrade procedure: `kubectl patch clusterextension example-extension --patch '{"spec":{"install":{"preflight":{"crdUpgradeSafety":{"enforcement":"None"}}}}}' --type=merge` and `kubectl patch clusterextension example-extension --patch '{"spec":{"source": {"catalog":{"upgradeConstraintPolicy":"SelfCertified"}}}}' --type=merge`, then set `version: <target_version>`; verify with `kubectl get clusterextension example-extension -o yaml`, `kubectl get crd | grep <extension_crd>` — [tutorials/downgrade-extension.md](https://github.com/operator-framework/operator-controller/blob/main/docs/tutorials/downgrade-extension.md)
- OpenShift forcing update/rollback: set `upgradeConstraintPolicy: SelfCertified` and `oc apply -f <extension_name>.yaml`; "You must verify the consequences of forcing a manual update or rollback. Failure to verify a forced update or rollback might have catastrophic consequences such as data loss." — [modules/olmv1-forcing-an-update-or-rollback.adoc (4.20)](https://github.com/openshift/openshift-docs/blob/enterprise-4.20/modules/olmv1-forcing-an-update-or-rollback.adoc)
- Catalog re-unpack triggers logged by catalogd: `unpack required: no cached catalog metadata found for this catalog`, `unpack required: no stored content found for this catalog`, `unpack required: current ClusterCatalog status differs from expected status`, `unpack required: catalog generation differs from observed generation`, `unpack required: poll duration has elapsed` — [internal/catalogd/controllers/core/clustercatalog_controller.go](https://github.com/operator-framework/operator-controller/blob/main/internal/catalogd/controllers/core/clustercatalog_controller.go)
- `pollIntervalMinutes` "Specifies the number of minutes for polling the remote registry for newer image digests. This field is optional. To disable polling, unset the field." — [tutorials/add-catalog.md](https://github.com/operator-framework/operator-controller/blob/main/docs/tutorials/add-catalog.md); kubectl-operator: polling "Only valid for tag based source image references" — [olmv1.md](https://github.com/operator-framework/kubectl-operator/blob/main/olmv1.md)
- Catalog HTTP client timeout raised "from 10s to 5m" in v1.11.0 (OCPBUGS-92037) — [v1.11.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.11.0)
- CRD upgrade safety: prohibited changes include scope change, removing a stored version, adding a required field, removing a field, changing a field type, adding/changing/removing defaults, adding or removing enum restrictions, tightening min/max; allowed include adding enum values, required->optional, loosening min/max, adding a new version; "the CRD Upgrade Safety preflight check will prevent the upgrade and log an error for an 'unknown change'"; disable via `.spec.install.preflight.crdUpgradeSafety.enforcement: None` ("You cannot disable individual field validators") — [concepts/crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md)
- Verbatim CRD safety errors: `validating upgrade for CRD "test.example.com" failed: CustomResourceDefinition test.example.com failed upgrade safety validation. "NoScopeChange" validation failed: scope changed from "Namespaced" to "Cluster"`; `... "NoStoredVersionRemoved" validation failed: stored version "v1alpha1" removed`; `... "NoExistingFieldRemoved" validation failed: crd/test.example.com version/v1alpha1 field/^.spec.pollInterval may not be removed`; `... "ChangeValidator" validation failed: version "v1alpha1", field "^": new required fields added: [pollInterval]` — [concepts/crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md)
- Resolution error format (`resolutionError.Error()`): optional prefix `error upgrading from currently installed version "<v>": `, then `found bundles for package "<pkg>" ` (when more than one) or `no bundles found for package "<pkg>" `, then optional `matching version "<v>" `, `in channels [<c>] `, and `in multiple catalogs with the same priority [<cats>]`; bundle validation failures are wrapped as `validating bundle "<name>": <err>` — [internal/operator-controller/resolve/catalog.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/resolve/catalog.go)
- Controller status messages during resolution: `failed to resolve bundle: <err>` and `failed to resolve bundle, retrying: <err>`; `retrying to get installed bundle` — [clusterextension_reconcile_steps.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/controllers/clusterextension_reconcile_steps.go)
- OpenShift CSV annotation to block cluster minor upgrades: `"olm.properties": '[{"type": "olm.maxOpenShiftVersion", "value": "<cluster_version>"}]'`; the `olm` cluster Operator reports extensions blocking cluster upgrade — [modules/olmv1-ocp-compat.adoc (4.20)](https://github.com/openshift/openshift-docs/blob/enterprise-4.20/modules/olmv1-ocp-compat.adoc)
- The project's own upgrade e2e: `test-upgrade-st2st-e2e` installs `https://github.com/operator-framework/operator-controller/releases/latest/download/install.sh` then upgrades to the locally built `standard-install.sh` (and `st2ex`, `ex2ex` variants) — [Makefile](https://github.com/operator-framework/operator-controller/blob/main/Makefile)

### Inferences
- A practical v1->v2 test on kind: add `olm.bundle` `<pkg>.v0.0.2` plus a channel entry `{name: <pkg>.v0.0.2, replaces: <pkg>.v0.0.1}` (or rely on semver), rebuild and push the catalog image, then either push to the same tag and wait for `pollIntervalMinutes`, or change `spec.source.image.ref` to the new tag/digest (which bumps generation and triggers `unpack required: catalog generation differs from observed generation`). Because operator-controller resolves from catalogd's cache, a cheap "force re-resolution" is to change the ClusterCatalog spec (e.g. a new digest ref) or delete and recreate the ClusterCatalog.
- Under semver rules a dev loop that versions bundles as `0.0.1` -> `0.0.2` will NOT auto-upgrade (patch upgrades are blocked when major and minor are both 0); use `0.1.0` -> `0.1.1` or `1.0.0` -> `1.0.1`, or set `upgradeConstraintPolicy: SelfCertified`, or pin `version:` explicitly.

### Gaps
- No primary source documents an explicit "force re-resolve" command; the inference above relies on catalogd's logged unpack triggers.

## Key question 6: Troubleshooting (errors, meanings, where logs live)

### Takeaway
Most failures surface as `Progressing` with `Reason: Retrying` (or `Blocked`) and `Installed` False/Unknown on the ClusterExtension, or `Serving: False` on the ClusterCatalog; the verbatim messages to grep for are `pre-authorization failed: service account requires the following permissions to manage cluster extension:` (OpenShift, Technology Preview preflight), `no bundles found for package "<pkg>"`, `found bundles for package "<pkg>" ... in multiple catalogs with the same priority`, `<Kind> '<name>' already exists in namespace '<ns>' and cannot be managed by operator-controller`, and `validating upgrade for CRD "<name>" failed: ...`; logs are in `olmv1-system` deployments `operator-controller-controller-manager` and `catalogd-controller-manager` (OpenShift: `openshift-operator-controller`, `openshift-catalogd`).

### Cited Findings

### Inferences
- Upstream v1.11+ no longer performs service-account preauthorization (no `pre-authorization` strings remain in `internal/`), so `pre-authorization failed` is an OpenShift/TechPreview-era message and an older-upstream message; on a current upstream install, RBAC errors from the extension's own ServiceAccount cannot occur because operator-controller applies as cluster-admin.
- Image pull failures show up as `Progressing` `Retrying` with the containers/image error text (for example TLS verification errors against an untrusted registry) and the fix is `--pull-cas-dir` content or `--global-pull-secret`; no canonical upstream message text was found for these.
- To bust a stale bundle cache during a dev loop, re-tag with a new tag or push by digest so the canonical ref changes (cache keys are canonical digest refs), or delete the ClusterExtension so the `cleanup-unpack-cache` finalizer purges it; re-pushing the same tag with different content is only noticed when the tag is re-resolved (catalog poll for ClusterCatalog; new resolution for bundles).

### Gaps
- No verbatim strings were found in code or docs for "service account not found", "user ... must have cluster-admin privileges", "unpack failed", or image pull errors; the project's draft troubleshooting page is not published (404).
- Red Hat's "Troubleshooting OLM v1" chapter (if it exists under a different slug) was not reachable; the 4.20/4.22 modules examined contain only the preflight-RBAC and catalog-selection troubleshooting references above.

## Key question 7: Hygiene for the local dev loop (re-triggering, cache, recreation)

### Takeaway
Change the bundle image, publish it under a new version in the FBC (semver-respecting), rebuild and push the catalog image, then bump the ClusterCatalog (new digest/tag) or wait for `pollIntervalMinutes`; for a hard reset delete the ClusterExtension (finalizers purge the unpack and content-manager caches) and recreate it.

### Cited Findings
- catalogd re-unpacks on generation change, missing cache/content, status mismatch or poll elapsed (messages listed in Q4) — [clustercatalog_controller.go](https://github.com/operator-framework/operator-controller/blob/main/internal/catalogd/controllers/core/clustercatalog_controller.go)
- catalogd garbage-collects on `--gc-interval` (default `12h`) — [cmd/catalogd/main.go](https://github.com/operator-framework/operator-controller/blob/main/cmd/catalogd/main.go)
- operator-controller cache path default `/var/cache/operator-controller`, changed in v1.12.0 to "avoid /var/cache/dnf conflict" — [cmd/operator-controller/main.go](https://github.com/operator-framework/operator-controller/blob/main/cmd/operator-controller/main.go), [v1.12.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.12.0)
- The unpack cache short-circuits with `image already unpacked` when the canonical reference's content exists — [image/cache.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/util/image/cache.go)
- `make e2e-setup` / `make e2e-teardown` provide a reusable kind cluster "for iterative e2e testing" — [Makefile](https://github.com/operator-framework/operator-controller/blob/main/Makefile)
- Tilt rebuilds and hot-swaps binaries for operator-controller/catalogd changes (`tilt up`), using `helm/tilt.yaml` (`featureSet: experimental`, `SingleOwnNamespaceInstallSupport` enabled, catalogd `APIV1MetasHandler`) — [docs/contribute/developer.md](https://github.com/operator-framework/operator-controller/blob/main/docs/contribute/developer.md), [helm/tilt.yaml](https://github.com/operator-framework/operator-controller/blob/main/helm/tilt.yaml)

### Inferences
- Always publish a new bundle version (and a new catalog tag or digest) per iteration rather than overwriting `v0.0.1`; overwriting a tag leaves operator-controller serving the cached digest until the catalog is re-resolved and the bundle ref changes.

### Gaps
- No documented command exists to purge operator-controller's cache in place; restarting the pod does not clear a persistent cache volume if one is configured (volume type on the standard manifest not verified).
