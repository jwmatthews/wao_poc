# WAO Needs a Catalog, Not a New Bundle

**Bottom line:** OLM v1 (operator-controller + catalogd) installs the same `registry+v1` bundle that classic OLM does, so the Workload Availability Operator (WAO) bundle at `bundle/` already clears every hard content rule OLM v1 enforces on OpenShift 4.18 through 4.22: it is `registry+v1`, supports only `AllNamespaces`, declares no `webhookdefinitions`, no `apiservicedefinitions`, no FBC dependency properties and ships nothing in `manifests/` except one CSV and thirteen CRDs. What WAO lacks is everything *around* the bundle: a File-Based Catalog (FBC) image labelled `operators.operatorframework.io.index.configs.v1` (the ConfigMap-backed `CatalogSource` of design decision D6 cannot be consumed by a `ClusterCatalog`, whose only source type is `Image`), a `ClusterCatalog` manifest, a pre-created install namespace with the PSA labels the SNR agents need, an installer ServiceAccount whose RBAC is a superset of everything the bundle renders (still mandatory on every shipped OpenShift release through 4.22, even though upstream v1.11.0 deprecated and now ignores `spec.serviceAccount`), a `ClusterExtension` manifest, and an FBC upgrade graph that respects OLM v1's highest-semver successor rule. The decisive design fact is that WAO creates the six component Deployments and their webhook configurations itself at runtime using OpenShift Service CA annotations, so OLM v1's own webhook support (unsupported on 4.18/4.19, Technology Preview on 4.20, GA on 4.21) is irrelevant to WAO's installability and WAO installs on all five releases. The costs OLM v1 adds are operational, not structural: deleting the `ClusterExtension` deletes all thirteen CRDs and therefore every remediation policy and template, no object OLM v1 did not create can be adopted (so a classic-OLM install of WAO or any medik8s operator must be fully removed first), and there is no OLM v0 to v1 in-place migration anywhere in Red Hat or upstream documentation.

## One cluster-scoped API and a five-release feature matrix

OLM v1 is two controllers in one repository exposing three cluster-scoped CRDs in API group `olm.operatorframework.io/v1`: `ClusterExtension` (what to install), `ClusterCatalog` (where to find it) and, only in the experimental channel, a revision object that OpenShift 4.21 lists as `ClusterExtensionRevision` and upstream v1.9.0 renamed to `ClusterObjectSet` ([architecture](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_architecture.md); [OCP 4.21 release notes](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/release_notes/index)). The `v1` API has been stable since operator-controller v1.0.0-rc1 on 2024-11-12, and OpenShift has only ever documented `olm.operatorframework.io/v1` from the 4.18 GA onward ([v1.0.0-rc1](https://github.com/operator-framework/operator-controller/releases/tag/v1.0.0-rc1)). Operator-controller resolves exactly one bundle from catalogd's served FBC content, renders the bundle into plain Kubernetes objects, and applies them as a synthetic Helm release (the GA path) or, behind the alpha `BoxcutterRuntime` gate, as an immutable `ClusterObjectSet` applied in thirteen ordered phases with readiness probes ([clusterobjectsets draft](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/concepts/clusterobjectsets.md)). Conceptually, OLM v1 replaces Subscription, CSV, OperatorGroup and InstallPlan with one object, treats every extension as a **cluster-wide singleton with single ownership of every managed object**, does constraint checking only (it never installs dependencies), and reconciles continuously instead of one-shot InstallPlans ([design decisions](https://operator-framework.github.io/operator-controller/project/olmv1_design_decisions/); [OCP 4.18 release notes](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html-single/release_notes/index)).

The `ClusterExtension` spec is small. `spec.namespace` is required, immutable, must already exist and is a DNS label; `spec.source.sourceType` has the single allowed value `Catalog`; `spec.source.catalog.packageName` is required and immutable; `version` is an optional semver constraint of at most 64 characters; `channels` is an optional list ANDed with `version`; `selector` is a label selector over `ClusterCatalog` objects, each of which is auto-labelled `olm.operatorframework.io/metadata.name=<name>`; `upgradeConstraintPolicy` is `CatalogProvided` (default) or `SelfCertified`; and `spec.install.preflight.crdUpgradeSafety.enforcement` is `Strict` (default) or `None` ([clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)). The version syntax accepts `=`, `!=`, `<`, `>`, `>=`, `<=`, wildcards (`1.2.x` means `>=1.2.0, <1.3.0`), tilde (`~1.2.3` means `>=1.2.3, <1.3.0`), caret (`^0.2.3` means `>=0.2.3, <0.3.0`) and `||` ([version ranges](https://operator-framework.github.io/operator-controller/concepts/version-ranges/)). Resolution picks the **highest semver that satisfies package AND version AND channels**, restricted to catalogs matched by `selector`, with ties broken by `ClusterCatalog.spec.priority` (higher wins), deprecated bundles deprioritised, and an error if ambiguity remains ([controlling catalog selection](https://operator-framework.github.io/operator-controller/concepts/controlling-catalog-selection/)). Because the four default Red Hat catalogs carry priorities `-100` (`openshift-redhat-operators`), `-200` (certified), `-300` (marketplace) and `-400` (community), a custom catalog left at the default priority `0` outranks all of them, so a package that exists in both places should be pinned with `selector` rather than by priority ([OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)).

Status is read from conditions. `Installed` is `True/Succeeded` when the bundle is installed and `False/Failed` when it is not; `Progressing` is `True/Succeeded` ("desired state reached"), `True/Retrying` for errors that may resolve on a later reconcile, or **`False/Blocked` for errors that require manual intervention**; `Deprecated` is a rollup of `PackageDeprecated`, `ChannelDeprecated` and `BundleDeprecated` ([common_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/common_types.go)). The installed bundle name and version live in `status.install.bundle`, but the installed image appears only in the `Installed` condition message (`Installed bundle <image@sha256:...> successfully`) ([OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)). Tooling should key on condition type plus status, not reason, for deprecation, because OCP 4.21 output shows `reason: Deprecated` with `status: "False"` while upstream v1.8.0 changed the healthy reason to `NotDeprecated` ([v1.8.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.8.0)). `ClusterCatalog` exposes `Serving` (`Available`, `Unavailable`, `UserSpecifiedUnavailable`) and `Progressing` (`Succeeded`, `Retrying`, `Blocked`), plus `status.resolvedSource.image.ref` with the digest catalogd actually unpacked and `status.urls.base` for the HTTPS endpoint ([clustercatalog_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clustercatalog_types.go)).

The single most consequential divergence between upstream and OpenShift is `spec.serviceAccount`. On upstream `main` since v1.11.0 (2026-07-23) the field is "a deprecated field and is completely ignored. OLMv1 is a single-tenant system where users with ClusterExtension write access are effectively delegated cluster-admin trust. The operator-controller runs with cluster-admin privileges", the `PreflightPermissions` and `SyntheticPermissions` gates were deleted, and a `ValidatingAdmissionPolicy` emits a warning when the field is set ([clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go); [v1.11.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.11.0); [PR #2770](https://github.com/operator-framework/operator-controller/pull/2770)). On every shipped OpenShift branch through `release-4.22` the Go type still says "The serviceAccount field is required" and the 4.18–4.22 Extensions guides document the installer-SA procedure as the install path ([release-4.22 types](https://github.com/openshift/operator-framework-operator-controller/blob/release-4.22/api/v1/clusterextension_types.go); [OCP 4.22 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/extensions/cluster-extensions)). The OpenShift enhancement tracking adoption (OCPSTRAT-3040) is `implementable` but names no target release ([service-account-deprecation.md](https://github.com/openshift/enhancements/blob/master/enhancements/olm/service-account-deprecation.md)). For WAO this means: **ship the installer SA and RBAC and keep `spec.serviceAccount.name` in the ClusterExtension**; the manifest stays schema-valid after the deprecation, where it merely produces a warning.

## The registry+v1 contract: honored, rejected and silently ignored

OLM v1 loads only `registry+v1` bundles and nothing else; native Helm-chart bundles were added in v1.4.0 behind a gate and removed again in v1.11.0, and no `plain` loader exists in the code ([limitations](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md); [v1.11.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.11.0)). From the bundle filesystem it reads `metadata/annotations.yaml` (only `operators.operatorframework.io.bundle.package.v1` is consumed; an empty package name fails `CheckPackageNameNotEmpty`), a **flat** `manifests/` directory (the error is `subdirectories are not allowed within the "manifests" directory of the bundle image filesystem`) containing exactly one CSV, and an optional `metadata/properties.yaml` that is merged into the `olm.properties` annotation and then never consumed; `metadata/dependencies.yaml` is not referenced anywhere in operator-controller ([source.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/bundle/source/source.go)). WAO's `bundle.Dockerfile` is the unmodified operator-sdk scaffold with `FROM scratch`, the standard labels and a flat `manifests/`; that is sufficient and nothing OLM v1-specific needs to be added to it.

Three hard rules are enforced at install time and surface in `status.conditions`. First, the CSV **must** mark `AllNamespaces` as `supported: true` unless the alpha `SingleOwnNamespaceInstallSupport` gate is on; the provider error is `unsupported bundle: bundle does not support AllNamespaces install mode`, `MultiNamespace` is unreachable from the public API, and `SingleNamespace`/`OwnNamespace` are "not recommended install modes as there is a hard limitation of only one instance of a given CRD in the cluster" ([provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go); [limitations](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)). Second, the catalog entry **must not** carry `olm.package.required`, `olm.gvk.required` or `olm.constraint` properties; the resolver rejects such bundles with `bundle %q has a dependency declared via property %q which is currently not supported` ([resolve/validation.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/resolve/validation.go)). Third, the CSV **must not** define owned `apiservicedefinitions`; the provider rejects them with `unsupported bundle: apiServiceDefintions are not supported` even though v1.12.0 merged an APIService renderer that remains gated off ([provider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/applier/provider.go); [v1.12.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.12.0)). A fourth, untested-at-install rule is that the `OperatorConditions` API does not exist under OLM v1: "Most extensions that rely on this API fail at start time" ([limitations](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_limitations.md)). WAO's CSV passes all four: `installModes` lists `AllNamespaces: supported: true` and the other three `false`, `apiservicedefinitions: {}`, there is no `dependencies.yaml` or `properties.yaml`, and the design brief lists operator-condition communication as out of scope; the implementer must confirm the Go code never creates an `OperatorCondition`.

Webhooks come only from `spec.webhookdefinitions`, each field of which (`type`, `generateName`, `deploymentName`, `containerPort`, `targetPort`, `webhookPath`, `rules`, `failurePolicy`, `sideEffects`, `admissionReviewVersions`, `conversionCRDs`) is copied verbatim into a generated `ValidatingWebhookConfiguration`, `MutatingWebhookConfiguration` or CRD `spec.conversion` ([generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)). Nothing in the renderer rewrites `failurePolicy`, so WAO's constraint of never changing a component webhook policy is preserved automatically for any webhook that passes through a CSV. The certificate is provisioned by a pluggable provider: cert-manager upstream, or on OpenShift the Service CA provider, which adds `service.beta.openshift.io/serving-cert-secret-name: <certName>` to the generated Service and `service.beta.openshift.io/inject-cabundle: "true"` to the webhook configurations and CRDs and creates no other objects ([openshift_serviceca.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/certproviders/openshift_serviceca.go)). The Service is named `<deploymentName with "." replaced by "-">-service`, the secret `<serviceName>-cert`, and the renderer removes any existing volume mounted at `/tmp/k8s-webhook-server/serving-certs` or `/apiserver.local.config/certificates` and mounts the secret at both paths, so an operator must read its serving cert from `/tmp/k8s-webhook-server/serving-certs/tls.crt|tls.key` ([certprovider.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/certprovider.go); [generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)). On OpenShift the cluster-olm-operator maps the `NewOLMWebhookProviderOpenshiftServiceCA` gate to `WebhookProviderOpenshiftServiceCA=true` **and forces `WebhookProviderCertManager=false`**, which matters because `getCertificateProvider()` prefers cert-manager when both gates are on ([cluster-olm-operator mapper.go](https://github.com/openshift/cluster-olm-operator/blob/release-4.21/internal/featuregates/mapper.go); [release-4.21 main.go](https://github.com/openshift/operator-framework-operator-controller/blob/release-4.21/cmd/operator-controller/main.go)). Webhook validators reject rules targeting the `olm.operatorframework.io` or `*` API groups or the `admissionregistration.k8s.io` webhook-configuration resources, require conversion webhooks only in `AllNamespaces`-only bundles, and require `spec.preserveUnknownFields: false` on converted CRDs ([validator.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/validators/validator.go)).

WAO sidesteps all of this because its CSV has no `webhookdefinitions`. The component webhook Services, Service CA annotations, cert mounts at `/tmp/k8s-webhook-server/serving-certs` and webhook configurations are created by WAO at runtime as operands (design brief D1), exactly as under classic OLM; OLM v1 never sees them, so the 4.18/4.19 "must not use webhooks" rule does not apply to WAO and the OCP 4.21 discovery query that filters on `.spec.webhookdefinitions == null` lists WAO as installable ([OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)). The one place OLM v1 touches these objects is RBAC: the installer SA must be able to grant WAO's `clusterPermissions` on `validatingwebhookconfigurations`, `mutatingwebhookconfigurations`, `deployments`, `daemonsets`, `services` and the rest, which is why the generated installer ClusterRole in `test/olmv1/rbac/wao/10-clusterrole.yaml` is as broad as the CSV.

Which CSV fields are honored and which are ignored is worth stating precisely, because an engineer coming from OLM v0 will expect the wrong things. The table below is assembled from the renderer and from a grep of operator-controller for each field.

|---|---|

"Other" objects in `manifests/` are restricted to operator-registry's `supportedResources` list, which operator-controller's `CheckObjectSupport` reuses: namespaced `Service`, `ServiceAccount`, `Role`, `RoleBinding`, `PrometheusRule`, `ServiceMonitor`, `Secret`, `ConfigMap`, `PodDisruptionBudget`, `NetworkPolicy`, `PodMonitor`; cluster-scoped `CustomResourceDefinition`, `ClusterRole`, `ClusterRoleBinding`, `PriorityClass`, `VerticalPodAutoscaler`, `ConsoleYAMLSample`, `ConsoleQuickStart`, `ConsoleCLIDownload`, `ConsoleLink`, `ConsolePlugin` ([supported_resources.go](https://github.com/operator-framework/operator-registry/blob/master/pkg/lib/bundle/supported_resources.go)). A `Deployment`, `Namespace`, `Job`, `Route`, webhook configuration, `APIService`, `SecurityContextConstraints`, `OperatorGroup` or any custom-resource instance in `manifests/` fails with `bundle contains unsupported resource: Name: %v, Kind: %v`, and every namespaced "other" object is forced into the install namespace whatever `metadata.namespace` it declares ([generators.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/render/registryv1/generators/generators.go)). WAO ships only the CSV and CRDs, so this is satisfied; if WAO later adds its `config/network-policy/allow-metrics-traffic.yaml` to the bundle, `NetworkPolicy` is an allowed kind on OCP 4.20+ ([OCP 4.20 release notes](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/release_notes/index)).

Two more rules shape WAO's lifecycle more than any content rule. The CRD upgrade safety preflight (crdify-based, fail-closed) blocks scope changes, stored-version removal, new required fields, removed fields, type changes, any default added/changed/removed, enum restrictions added or values removed, and tightened min/max; it allows new enum values, required-to-optional, loosened min/max and new CRD versions; it logs "unknown change" and blocks anything it cannot classify; it is skipped when the CRD does not yet exist; and it can be disabled only wholesale with `enforcement: None` ([crd-upgrade-safety.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/crd-upgrade-safety.md); [crdupgradesafety.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/rukpak/preflights/crdupgradesafety/crdupgradesafety.go)). Since WAO re-ships twelve upstream medik8s CRDs unchanged, **every component version bump in `release-set.yaml` is a CRD upgrade that must pass this preflight**, and the implementer should diff old and new CRDs against the prohibited list before publishing. The single-owner rule states that "a Kubernetes resource can only be owned by a single `ClusterExtension` at a time" and that bundles providing a CRD "can only be installed once"; a pre-existing CRD fails with `CustomResourceDefinition '<name>' already exists in namespace '<ns>' and cannot be managed by operator-controller` ([single-owner-objects.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/single-owner-objects.md); [errors.go](https://github.com/operator-framework/operator-controller/blob/main/internal/operator-controller/action/error/errors.go)). The Helm applier's check is Helm's own ownership validation on the `app.kubernetes.io/managed-by` label and `meta.helm.sh/release-name`/`release-namespace` annotations ([helm validate.go](https://github.com/helm/helm/blob/main/pkg/action/validate.go)). This is consistent with design decision D8 (WAO owns all thirteen CRDs, so standalone medik8s installs cannot coexist) and it means a classic-OLM WAO install, which leaves CRDs behind on CSV deletion, blocks an OLM v1 install of the same bundle until the CRDs are removed. The repository's experiments 0002 and 0003 (`test/olmv1/README.md`) found that pre-annotating CRDs with the Helm release keys lets OLM v1 take them over without CR loss; that is Helm behaviour, not a documented OLM v1 feature, and it must stay an operator-run migration step rather than something WAO's code does, since WAO never adopts objects it did not create.

## Building the file-based catalog: three blobs, one label, one semver trap

An FBC is a directory of JSON or YAML blobs. Each package needs exactly one `olm.package` (with `name`, `defaultChannel`, optional `description`, `icon`), at least one `olm.channel` (`package`, `name`, `entries[]` of `name`, optional `replaces`, `skips`, `skipRange`), and one or more `olm.bundle` blobs (`package`, `name`, `image`, `properties[]`, optional `relatedImages[]`), plus an optional `olm.deprecations` blob whose package, channel and bundle references map to the `PackageDeprecated`, `ChannelDeprecated` and `BundleDeprecated` conditions ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/extensions/index); [declcfg.go](https://github.com/operator-framework/operator-registry/blob/master/alpha/declcfg/declcfg.go)). Operator-controller reads the bundle version from the `olm.package` property, which is required, must be unique per bundle and must be valid semver; `olm.gvk` is harmless; `olm.csv.metadata` (install modes, description, annotations) is what the documented discovery queries read and replaces the deprecated `olm.bundle.object`, which "causes major performance issues when loading and serving file-based catalogs" ([file-based catalogs reference](https://olm.operatorframework.io/docs/reference/file-based-catalogs/)). Render bundles with `opm render <bundle> --output yaml --migrate-level bundle-object-to-csv-metadata` to get the modern property set ([render cmd.go](https://github.com/operator-framework/operator-registry/blob/master/cmd/opm/render/cmd.go); [migrations.go](https://github.com/operator-framework/operator-registry/blob/master/alpha/action/migrations/migrations.go)). The recommended layout is one subdirectory per package so that "each subdirectory in the directory hierarchy is a self-contained catalog", with `.indexignore` for non-catalog files ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/extensions/index)).

The documented end-to-end path is `opm init` to emit the `olm.package` blob, `opm render <bundle-image> --output yaml >> index.yaml` for each bundle, a hand-written `olm.channel` block (the entry name must be `<package>.v<version>`, "Otherwise, the entry fails to pass the `opm validate` command"), `opm validate <dir>` (exit code 0 for valid), `opm generate dockerfile <dir> -i registry.redhat.io/openshift4/ose-operator-registry-rhel9:v4.<y>` and a `podman build`/`push` ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/extensions/index)). Catalogd needs far less than the generated Dockerfile provides: it reads the image config label `operators.operatorframework.io.index.configs.v1`, extracts only that directory, and treats a missing label on a digest-pinned reference as a terminal error; the `opm serve --cache-only` layer and the `opm` entrypoint exist only for OLM v0's gRPC `CatalogSource` pods ([image/cache.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/util/image/cache.go); [generate_dockerfile.go](https://github.com/operator-framework/operator-registry/blob/master/alpha/action/generate_dockerfile.go)). Operator-controller's own e2e therefore builds its catalog as `FROM scratch` / `ADD catalog /configs` / `LABEL operators.operatorframework.io.index.configs.v1=/configs` ([setup.sh](https://github.com/operator-framework/operator-controller/blob/main/test/extension-developer-e2e/setup.sh)). For WAO, which still needs to serve classic OLM too, the `ose-operator-registry-rhel9` base keeps one image usable as both a `CatalogSource` and a `ClusterCatalog`; the scratch variant is the right choice for the OLM v1-only PoC loop and is what `test/olmv1/README.md` already describes for experiment 0003. Either way the Makefile's `catalog-build` target, which runs the deprecated SQLite-era `opm index add --mode semver` with `opm` v1.55.0, must be replaced, and design decision D6's ConfigMap-backed `CatalogSource` cannot be reused because `ClusterCatalog.spec.source.type` admits only `Image` ([clustercatalog_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clustercatalog_types.go)).

Templates can generate the graph. The basic template (`olm.template.basic`) is the FBC with bundle images in place of rendered blobs; the semver template (`olm.semver`) takes `Candidate`, `Fast` and `Stable` bundle lists and emits `candidate-v0.1`-style minor channels (`GenerateMinorChannels` defaults to true) and `candidate-v0` major channels, with `skips` inside a channel and `replaces` across minor boundaries, never crossing a major version; it requires `csv.spec.version` and "if any bundles differ only by build metadata the render attempt will generate a fatal error" ([catalog templates](https://olm.operatorframework.io/docs/reference/catalog-templates/)). Red Hat's certification and community pipelines are FBC-first and recommend the semver template through `ci.yaml` `fbc.catalog_mapping` ([fbc_workflow.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/fbc_workflow.md)). For a single-channel PoC the hand-written channel is simpler; adopt the semver template when WAO publishes more than one stream.

The `ClusterCatalog` manifest is minimal, and the OCP form is:

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterCatalog
metadata:
  name: wao-poc
spec:
  priority: 1000
  source:
    type: Image
    image:
      ref: <registry>/<org>/wao-catalog:v0.1.0   # or @sha256:... (then omit pollIntervalMinutes)
      pollIntervalMinutes: 10
```

`pollIntervalMinutes` is forbidden with digest references, a tag reference is re-resolved on the poll interval, and `status.resolvedSource.image.ref` records the digest actually unpacked, which is what evidence should capture ([clustercatalog_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clustercatalog_types.go); [OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)). On OpenShift both controllers pull with `--global-pull-secret=openshift-config/pull-secret`, so a catalog in a private registry needs its credentials in the cluster pull secret; for the PoC's in-cluster image registry the repository already grants `system:image-puller` to `system:serviceaccounts:openshift-catalogd` and `system:serviceaccounts:openshift-operator-controller` (`test/olmv1/README.md`), which matches how the controllers pull images themselves rather than through the kubelet ([release-4.21 manifests.yaml](https://github.com/openshift/operator-framework-operator-controller/blob/release-4.21/openshift/operator-controller/manifests.yaml)).

Upgrade graph rules differ from OLM v0 in one way that matters. OLM v1 honours `replaces`, `skips` and `skipRange`, but "does not have a concept of a `replaces` chain": it finds every channel entry whose edge covers the installed version and picks the **highest semver successor**, whereas OLM v0 picks the one closest to the channel head ([upgrade-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/upgrade-support.md)). Under the default `CatalogProvided` policy only successors are eligible; `SelfCertified` ignores the graph and allows any upgrade, downgrade or sidegrade and is described as dangerous ([clusterextension_types.go](https://github.com/operator-framework/operator-controller/blob/main/api/v1/clusterextension_types.go)). Automatic upgrades never cross a major version, and within major zero the upstream doc states that patch upgrades are not automatic when minor is also zero (`0.0.1` to `0.0.2`) and minor hops (`0.1.0` to `0.2.0`) are not automatic, while `0.1.0` to `0.1.5` is ([upgrade-support.md](https://github.com/operator-framework/operator-controller/blob/main/docs/concepts/upgrade-support.md)). **WAO's CSV is `0.1.0`**, so its first automatic upgrade can only be `0.1.z`; a move to `0.2.0` or `1.0.0` will require users to set `SelfCertified` unless the project versions WAO as `1.0.0` from the start, which is the simplest fix. The notes could not confirm whether an explicit `replaces` edge overrides the major-zero rule, so the implementer should test it on kind before relying on either reading. Red Hat's channel conventions apply unchanged: each new version carries `replaces: <immediately previous>` plus a `skipRange` covering older versions, one head per channel, every previously published bundle must keep an upgrade path, and "OLM will not reinstall an installed bundle if the contents of that bundle are updated in the catalog", so a broken bundle is fixed by publishing a successor, never by overwriting ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/extensions/index)). Bundle versions must be strict semver, and build-metadata-only variants must be avoided because v1.5.0 added build-metadata precedence and the semver template refuses them ([operator-controller releases](https://github.com/operator-framework/operator-controller/releases)).

Disconnected delivery is the oc-mirror plugin v2 path: list the custom catalog under `operators[].catalog` in an `ImageSetConfiguration` (registry reference or `oci:///path`), run `oc mirror ... --v2`, and `oc apply -f working-dir/cluster-resources`, which contains generated `ImageDigestMirrorSet`, `ImageTagMirrorSet`, `CatalogSource` (for OLM Classic) and `ClusterCatalog` objects; the generated `ClusterCatalog.spec.source.image.ref` must not be hand-edited ([OCP 4.20 Disconnected environments](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/disconnected_environments/index)). Mirroring by digest is why WAO's `relatedImages` must stay digest-pinned, which they already are.

## Installing on OpenShift today: an installer that must already hold everything it grants

On every OpenShift release through 4.22 the install is a six-object sequence: namespace, installer `ServiceAccount`, installer `ClusterRole`, `ClusterRoleBinding`, optional namespace `Role`/`RoleBinding`, then the `ClusterExtension` ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions); [derive-service-account.md v1.10.0](https://github.com/operator-framework/operator-controller/blob/v1.10.0/docs/howto/derive-service-account.md)). The installer SA exists because "OLMv1 itself does not have cluster-wide admin permissions" in this model and Kubernetes RBAC escalation prevention means the creator of a role must already hold (or be able to `escalate`/`bind`) the permissions it grants; therefore the installer's privileges must be a superset of the bundle's `permissions` and `clusterPermissions`, and the installer SA and the bundle's SA must not share a name ([permission-model.md v1.10.0](https://github.com/operator-framework/operator-controller/blob/v1.10.0/docs/concepts/permission-model.md)). Red Hat's required list is explicit: `clusterextensions/finalizers` `update` scoped to the extension name (because OpenShift runs the `OwnerReferencesPermissionEnforcement` admission plugin), `clusterroles` and `clusterrolebindings` management, CRDs, Deployments, ServiceAccounts, Services, ConfigMaps, every cluster-scoped and namespaced bundle object, and the full CSV `permissions`/`clusterPermissions`; `create`, `list` and `watch` cannot be scoped by `resourceNames`, while `get`/`update`/`patch`/`delete` can be scoped once the generated `<package_name>.<hash>` names are known after the first install ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions)). Both Red Hat and upstream offer a test-only shortcut (a `*`/`*`/`*` ClusterRole or binding `cluster-admin`) with the warning that it must never be used in production ([derive-service-account.md v1.10.0](https://github.com/operator-framework/operator-controller/blob/v1.10.0/docs/howto/derive-service-account.md)). The Technology Preview preflight check reports gaps as `Progressing=False/Retrying` with `pre-authorization failed: service account requires the following permissions to manage cluster extension: Namespace:"" APIGroups:[] Resources:[services] Verbs:[list,watch] ...`, where `Namespace:""` means cluster scope and `APIGroups:[]` the core group, and it distinguishes missing verbs, privilege escalation and missing role references ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions)). If a later bundle needs more permissions, "OLM v1 halts the update process until a cluster administrator grants those permissions" ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions)).

WAO is an unusually heavy case for this model. Its CSV carries the union of the six components' rules (over a hundred cluster rules, several with `verbs: ["*"]`, `use` on the `privileged` SCC, and management of `validatingwebhookconfigurations`, `daemonsets`, `machines` and more), so the installer ClusterRole must hold all of that too. The repository already has a generator, `test/olmv1/gen-installer-rbac.py`, that derives `rbac/wao/{00-serviceaccount,10-clusterrole,20-clusterrolebinding,30-clusterextension}.yaml` from the CSV following the OCP 4.22 procedure, deliberately leaves the generated-name rules unscoped (its README notes that `resourceNames: ["*"]` is a documentation placeholder with no wildcard semantics in Kubernetes RBAC), and treats the first install's preflight report as the authority for tightening. That generator is the right starting point for product RBAC; the implementer should move namespace-scoped groups (Deployments, ServiceAccounts, Services, ConfigMaps, Roles) into a `Role` in the install namespace and scope `get/update/patch/delete` by the names observed after the first install. The ClusterExtension that goes with it already exists in `test/olmv1/rbac/wao/30-clusterextension.yaml`; its canonical shape is:

```yaml
apiVersion: olm.operatorframework.io/v1
kind: ClusterExtension
metadata:
  name: workload-availability-operator
spec:
  namespace: openshift-workload-availability
  serviceAccount:
    name: wao-installer            # required on OCP 4.18-4.22; ignored with a warning upstream >= v1.11
  source:
    sourceType: Catalog
    catalog:
      packageName: workload-availability-operator
      channels: [alpha]
      version: "0.1.0"             # pin; or "~0.1" for z-stream auto-updates
      upgradeConstraintPolicy: CatalogProvided
      selector:
        matchLabels:
          olm.operatorframework.io/metadata.name: wao-poc
```

The documented variants are: pin to an exact version to disable automatic updates; `version: ">=3.0, <3.6"` for range auto-updates; `version: "~2.3"` for z-stream only; `channels: [stable]` with `version: "!=1.3.2"` to exclude a bad release; `upgradeConstraintPolicy: SelfCertified` plus, for downgrades, `crdUpgradeSafety.enforcement: None` ([how-to-pin-version.md](https://github.com/operator-framework/operator-controller/blob/main/docs/howto/how-to-pin-version.md); [how-to-channel-based-upgrades.md](https://github.com/operator-framework/operator-controller/blob/main/docs/howto/how-to-channel-based-upgrades.md); [downgrade tutorial](https://operator-framework.github.io/operator-controller/tutorials/downgrade-extension/)). Comparison strings must be double-quoted, and `selector` should always pin WAO to its own catalog so the package can never be shadowed by or shadow a same-named package in a default catalog. Combining `channels` with a bounded `version` range is the safest GitOps shape. Because OLM v1 does not create the namespace and the `suggested-namespace-template` annotation is ignored in the standard channel, the install documentation must tell admins to create `openshift-workload-availability` themselves with the labels WAO's operands need; `test/olmv1/01-namespace.sh` creates it with privileged PSA labels, which the SNR node agents require. Upstream's replacement for the installer model, once an OpenShift release adopts it, is RBAC on who may write `ClusterExtension` objects plus a `ValidatingAdmissionPolicy` constraining `spec.namespace`, catalog selector labels, package and version allowlists, `upgradeConstraintPolicy != "SelfCertified"` and `crdUpgradeSafety.enforcement != "None"` ([how-to-protect-olmv1-api-access.md](https://github.com/operator-framework/operator-controller/blob/main/docs/howto/how-to-protect-olmv1-api-access.md)).

Lifecycle semantics are strict. Upgrades are triggered by editing `version`/`channels` or by the catalog publishing a new successor; `kubectl patch clusterextension <name> --type=merge -p '{"spec":{"source":{"catalog":{"version":"<new>"}}}}'` is the documented manual form ([upgrade tutorial](https://operator-framework.github.io/operator-controller/tutorials/upgrade-extension/)). A failed upgrade leaves the previously installed bundle running and reports `Progressing=True/Retrying` (for example `error upgrading from currently installed version "1.15.2": no bundles found for package "<pkg>" matching version "9.x"`) while `Installed` stays `True`; there is no automatic rollback, and "OLM v1 does not support automatic updates to the next major version or rollbacks to an earlier version" without `SelfCertified` ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions)). Deletion is the sharpest edge: "You can delete an Operator and its custom resource definitions (CRDs) by deleting the ClusterExtension custom resource", the finalizers `olm.operatorframework.io/cleanup-unpack-cache` and `cleanup-contentmanager-cache` only purge OLM's caches, the namespace and installer RBAC survive and must be removed by hand, and **there is no retain-CRDs option** as of October 2026 (a Red Hat article says one is planned) ([OCP 4.20 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/extensions/cluster-extensions); [uninstall tutorial](https://operator-framework.github.io/operator-controller/tutorials/uninstall-extension/); [developers.redhat.com](https://developers.redhat.com/articles/2025/06/02/manage-operators-clusterextensions-olm-v1)). For WAO that means deleting the `ClusterExtension` deletes all thirteen CRDs and with them every `NodeHealthCheck`, template, config and in-flight remediation; the user documentation must say so, and the recommended order is to disable every component in `WorkloadAvailabilityConfig`, wait for WAO to finish, then delete the extension, the namespace and the installer RBAC. The repository's experiment 0002 found `oc delete clusterextension --cascade=orphan` preserves rendered objects; that is a Kubernetes garbage-collection behaviour, not a documented OLM v1 feature.

OLM v0 and v1 coexist on every release since 4.18 ("enabled by default alongside OLM (Classic)"), read the same Red Hat index images through `ClusterCatalog` and `CatalogSource` respectively, and no release note deprecates OLM Classic ([OCP 4.21 Operators guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/operators/index)). There is no in-place migration: the only migration content that exists maps configuration (OperatorGroup to `watchNamespace`, `Subscription.spec.config` to `deploymentConfig`, with volumes and volumeMounts merging by name instead of appending), and the upstream design page still says the v0-to-v1 migration design is future work ([configure-bundles.md](https://github.com/operator-framework/operator-controller/blob/main/docs/draft/howto/configure-bundles.md); [OCP 4.22 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/extensions/cluster-extensions); [design decisions](https://github.com/operator-framework/operator-controller/blob/main/docs/project/olmv1_design_decisions.md)). The practical implication for WAO is a documented, destructive procedure: back up operand CRs, delete the Subscription and CSV, delete the CRDs (or the OLM v1 install is refused), create namespace, RBAC and `ClusterExtension`, restore CRs. Experiment 0005 in `test/olmv1/README.md` ran a variant of this on 4.22.1 and found two additional manual clean-up steps (classic-OLM static RBAC labelled `olm.owner=<csv>` and a stale `SelfNodeRemediationConfig`) that the implementer should script.

## OpenShift metadata OLM v1 carries but does not read

OpenShift-specific CSV metadata is inert to operator-controller but still required by OperatorHub, the certification policy and the Red Hat index build, so a bundle that serves both runtimes must carry it. The `features.operators.openshift.io/*` annotations (`disconnected`, `fips-compliant`, `proxy-aware`, `tls-profiles`, `token-auth-aws`, `token-auth-azure`, `token-auth-gcp`, optional `cnf`/`cni`/`csi`) take the string values `"true"`/`"false"`, replaced the deprecated `operators.openshift.io/infrastructure-features` array in 4.14, and the seven non-plugin keys are listed as required by the 2025 certification policy alongside `categories`, `description`, `containerImage`, `createdAt`, `support`, `operators.openshift.io/valid-subscription`, `spec.relatedImages` for every image and `spec.customresourcedefinitions.owned` for every CRD ([OCP 4.15 Operators guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.15/html-single/operators/index); [certification policy guide](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_openshift_software_certification_policy_guide/index)). WAO's CSV currently has `capabilities`, `categories`, `createdAt`, `description`, `support`, `repository` and the suggested-namespace pair, but **no `features.operators.openshift.io/*` annotations, no `containerImage`, no `operators.openshift.io/valid-subscription` and no `operatorframework.io/arch.*`/`os.*` labels**; it should at minimum add `disconnected: "true"` (its images are digest-pinned), explicit `"false"` for the rest until proven, and `containerImage` pointing at the digest-pinned WAO image.

`olm.maxOpenShiftVersion` is the one CSV annotation OLM v1 honours on OpenShift: set as `"olm.properties": '[{"type": "olm.maxOpenShiftVersion", "value": "4.y"}]'`, it makes the `olm` ClusterOperator report `Upgradeable=False` before a cluster minor update the operator does not support, comparing major.minor only ([OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)). Use it only when a bundle genuinely cannot run on the next minor, because admins then cannot upgrade their cluster with WAO installed. `com.redhat.openshift.versions` in `metadata/annotations.yaml` (`"v4.18"` open-ended, `"v4.18-v4.22"` ranged, `"=v4.21"` exact, no spaces, `v` prefix) is a catalog-inclusion control enforced by Red Hat's index build, not by OLM at runtime, and is mandatory for certification ([certification workflow guide](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_software_certification_workflow_guide/index); [packaging-required-criteria-ocp.md](https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/docs/users/packaging-required-criteria-ocp.md)). WAO's `annotations.yaml` lacks it and should add `com.redhat.openshift.versions: "v4.18"`.

Platform requirements are unchanged from OLM v0 but the delivery mechanisms differ. The operator must run under `restricted-v2` (certification requires "the most restrictive Security Context Constraint"); WAO's Deployment already sets `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]` and `seccompProfile.type: RuntimeDefault` and leaves `runAsUser` unset so `MustRunAsRange` can assign it ([OCP 4.20 Authentication guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/authentication_and_authorization/index); [policy guide](https://docs.redhat.com/en/documentation/red_hat_software_certification/2025/html-single/red_hat_openshift_software_certification_policy_guide/index)). FIPS readiness is a build concern: Red Hat Go Toolset with `CGO_ENABLED=1`, dynamic linking, no `-no_openssl` tag, optionally `GOEXPERIMENT=strictfipsruntime` ([FIPS and Go Toolset](https://developers.redhat.com/articles/2025/01/23/fips-mode-red-hat-go-toolset)). The gap that OLM v1 opens is proxy and trusted-CA injection: under OLM Classic the cluster-wide proxy is injected automatically and the trusted CA bundle is mounted through `Subscription.spec.config`, but **no OLM v1 document states that proxy variables or the CA bundle are injected into extension Deployments**, there is no `Subscription.spec.config` surface, and the only post-install customisation is `spec.config.inline.deploymentConfig`, Technology Preview in 4.22 and disabled before that ([OCP 4.20 Operators guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/operators/index); [OCP 4.22 release notes](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html-single/release_notes/index)). Until this is confirmed on a cluster, WAO should read the cluster `Proxy` object itself if it ever needs egress, propagate the variables to operands, and mount a `config.openshift.io/inject-trusted-cabundle: "true"` ConfigMap from its own Deployment spec rather than expect OLM to add it. OLM v1 also "does not automatically configure or manage role-based access control (RBAC) for users to interact with the APIs provided by installed packages"; aggregated ClusterRoles with `rbac.authorization.k8s.io/aggregate-to-view: "true"` and friends are the documented pattern, and WAO's bundle may ship them as allowed `ClusterRole` objects ([how-to-grant-api-access.md](https://github.com/operator-framework/operator-controller/blob/main/docs/howto/how-to-grant-api-access.md)).

No tool validates OLM v1 compatibility. `operator-sdk bundle validate ./bundle --select-optional suite=operatorframework` runs the Operator Framework suite (`good-practices`, `alpha-deprecated-apis`, `capabilities`, `categories`, `operatorhubv2`, `multiarch`), `opm validate <dir>` validates FBC structure and channel invariants, `opm alpha bundle validate` checks bundle image layout, and Red Hat `preflight check operator` runs certification checks including `DeployableByOLM`, which deploys through OLM Classic and therefore says nothing about OLM v1 ([operator-sdk bundle validate](https://sdk.operatorframework.io/docs/cli/operator-sdk_bundle_validate/); [opm validate](https://github.com/operator-framework/operator-registry/blob/master/cmd/opm/validate/validate.go); [openshift-preflight README](https://github.com/redhat-openshift-ecosystem/openshift-preflight/blob/main/README.md)). The only published OLM v1 "filter" is the `opm render <index> | jq` query selecting `olm.csv.metadata` bundles with `AllNamespaces.supported == true` and `.spec.webhookdefinitions == null` ([OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)). WAO's `hack/check-bundle.py` should therefore grow an OLM v1 check: `AllNamespaces` supported, no `webhookdefinitions` (or, if ever added, only on OCP 4.21+), `apiservicedefinitions.owned` empty, no `*.required`/`olm.constraint` properties in the rendered FBC, `manifests/` flat and limited to allowed kinds, DNS-1123 deployment names, and semver `spec.version`. The authoritative test remains a live install with `.status.conditions` read back.

## A kind loop that pushes to a registry, never `kind load`

The upstream dev loop starts with `curl -L -s https://github.com/operator-framework/operator-controller/releases/download/v1.12.0/install.sh | bash -s`, which installs cert-manager v1.18.2 if absent, applies `operator-controller.yaml` into `olmv1-system` (deployments `catalogd-controller-manager` and `operator-controller-controller-manager`), and optionally the `operatorhubio` catalog; the latest release on 2026-10-10 is v1.12.0 (2026-09-24) and the project pins kind v0.32.0, opm v1.60.0, operator-sdk v1.41.1 and controller-gen v0.21.0, with kindest/node images for Kubernetes 1.33 through 1.36 ([v1.12.0](https://github.com/operator-framework/operator-controller/releases/tag/v1.12.0); [install.tpl.sh](https://github.com/operator-framework/operator-controller/blob/main/scripts/install.tpl.sh); [.bingo/Variables.mk](https://github.com/operator-framework/operator-controller/blob/main/.bingo/Variables.mk)). The standard release manifest enables only `WebhookProviderCertManager`; the experimental manifest (`install-experimental.sh`) adds `BoxcutterRuntime`, `BundleReleaseSupport`, `DeploymentConfig`, `SingleOwnNamespaceInstallSupport` and catalogd's `APIV1MetasHandler`/`GraphQLCatalogQueries` ([values.yaml](https://github.com/operator-framework/operator-controller/blob/main/helm/olmv1/values.yaml); [experimental.yaml](https://github.com/operator-framework/operator-controller/blob/main/helm/experimental.yaml)). Two upstream-versus-OpenShift differences shape what a kind test can prove: upstream v1.12.0 ignores `spec.serviceAccount` and runs as cluster-admin, so **installer RBAC bugs are invisible on kind**, and upstream uses cert-manager for webhooks while OpenShift uses Service CA. Since WAO handles its own certificates, the second difference does not affect it, but the first means RBAC must be validated on a disposable OpenShift 4.18–4.22 cluster, where the preflight check (TechPreview) or a plain install failure will expose gaps. The project's kind config enables the `OwnerReferencesPermissionEnforcement` admission plugin to mimic OpenShift ([kind-config.yaml](https://github.com/operator-framework/operator-controller/blob/main/kind-config/kind-config.yaml)).

Local images need a registry. Catalogd and operator-controller pull with the containers/image library inside their own pods, honouring `--pull-cas-dir` for CA trust and `--global-pull-secret` for auth, so `kind load docker-image` (which seeds containerd on the nodes) does not make an image visible to them; the project's own extension-developer e2e deploys an in-cluster TLS registry at `docker-registry.operator-controller-e2e.svc:5000` with a cert-manager certificate from the `olmv1-ca` issuer and pushes bundle and catalog images with `crane` over a port-forward ([main.go](https://github.com/operator-framework/operator-controller/blob/main/cmd/operator-controller/main.go); [registry.go](https://github.com/operator-framework/operator-controller/blob/main/test/internal/registry/registry.go); [setup.sh](https://github.com/operator-framework/operator-controller/blob/main/test/extension-developer-e2e/setup.sh)). No supported way to use a plain-HTTP registry was found. The loop is then: build and push the bundle image, write the FBC with `olm.package`, `olm.bundle` (image by digest, `olm.package` property) and `olm.channel`, build the scratch catalog image with the `configs.v1` label and push it, apply the `ClusterCatalog`, `kubectl wait --for=condition=Serving=True clustercatalog/<name> --timeout=60s`, apply the `ClusterExtension`, and read `kubectl get clusterextension <name> -o jsonpath-as-json="{.status.install}"` plus the conditions ([getting started](https://operator-framework.github.io/operator-controller/getting-started/olmv1_getting_started/)). Catalog content is inspected with `kubectl -n olmv1-system port-forward svc/catalogd-service 8443:443` and `curl -k https://localhost:8443/catalogs/<name>/api/v1/all | jq`; on OpenShift the equivalent namespace is `openshift-catalogd` (from `status.urls.base`), though Red Hat documents only `opm render <index> | jq` ([catalog queries](https://operator-framework.github.io/operator-controller/howto/catalog-queries/); [OCP 4.21 Extensions](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html-single/extensions/index)). The `kubectl operator olmv1` krew plugin exists but has not been released since v0.6.0 in January 2025 and still defaults the service account, so it is convenience tooling only ([kubectl-operator releases](https://github.com/operator-framework/kubectl-operator/releases)).

Upgrade testing follows from the cache rules. Catalogd re-unpacks when the spec generation changes, when the poll interval elapses on a tag reference, or when its cache is missing; the log lines are `unpack required: catalog generation differs from observed generation` and `unpack required: poll duration has elapsed` ([clustercatalog_controller.go](https://github.com/operator-framework/operator-controller/blob/main/internal/catalogd/controllers/core/clustercatalog_controller.go)). Operator-controller caches bundles by canonical digest and logs `image already unpacked`, so re-pushing the same tag is only noticed once the catalog re-resolves and the bundle reference changes ([image/cache.go](https://github.com/operator-framework/operator-controller/blob/main/internal/shared/util/image/cache.go)). The practical rule is **always publish a new bundle version and a new catalog tag or digest per iteration**; a v1 to v2 test adds an `olm.bundle` and a channel entry with `replaces`, rebuilds and pushes the catalog, bumps the `ClusterCatalog` ref (or waits for the poll), and watches `status.install.bundle.version` change. Version the dev loop as `0.1.0` to `0.1.1` or `1.0.0` to `1.0.1`, never `0.0.1` to `0.0.2`, because of the major-zero rule. A hard reset is deleting the `ClusterExtension`, whose finalizers purge both caches, and recreating it. A GitHub Actions job can mirror the project's `e2e.yaml`: checkout, setup-go, `kind create cluster --image kindest/node:v1.34.8`, run the release `install.sh`, deploy the in-cluster registry, build and push, apply, `kubectl wait --for=condition=Installed=True clusterextension/<name>`, and on failure collect a `support-bundle` or the two controller deployments' logs ([e2e.yaml](https://github.com/operator-framework/operator-controller/blob/main/.github/workflows/e2e.yaml)).

## Live-cluster verification on OpenShift 5.0 rc5

A read-only inspection of the OCP 5.0 rc5 test cluster (`5.0.0-rc.5`, default feature set, 2026-10-10) checked the platform claims above against a shipped 5.0 payload; the evidence and per-question details are in [07-live-cluster-ocp-5.0-rc5.md](../research_notes/OLM%20v1%20operator%20requirements/07-live-cluster-ocp-5.0-rc5.md). The `spec.serviceAccount` deprecation has reached OpenShift: on 5.0 rc5 the field is optional, its CRD description reads "deprecated field and is completely ignored", a warn-only `ValidatingAdmissionPolicy` (`clusterextension-serviceaccount-deprecated`, `validationActions: [Warn]`) emits the warning on create and update, and the operator-controller ServiceAccount is bound to `cluster-admin`. A server-side dry run of a `ClusterExtension` carrying `spec.serviceAccount.name` succeeded with exactly that warning, so the recommendation to keep the field for 4.18–4.22 and accept a warning on 5.0 holds. The field remains immutable once set, so a future manifest must clear it rather than rename it.

The 5.0 rc5 build is a downstream synchronisation of upstream `operator-controller` from 2026-08-12, after v1.11.0 and before v1.12.0. Only `WebhookProviderOpenshiftServiceCA` is on by default; `BoxcutterRuntime`, `DeploymentConfig`, `SingleOwnNamespaceInstallSupport`, `BundleReleaseSupport`, `WebhookProviderCertManager` and catalogd's `APIV1MetasHandler`/`GraphQLCatalogQueries` are off, and `NewOLMBoxCutterRuntime`, `NewOLMCatalogdAPIV1Metas`, `NewOLMConfigAPI` and `NewOLMOwnSingleNamespace` are disabled feature gates. No `ClusterObjectSet` or `ClusterExtensionRevision` CRD exists, yet the `ClusterExtension` CRD is generated from the experimental set, so `spec.progressDeadlineMinutes`, `status.activeRevisions` and `status.install.bundle.release` are present in the schema. `spec.config` accepts only `configType: Inline` with a free-form `inline` object, and there is still no CRD-retention field. cert-manager is not installed and not needed.

On the catalog side, catalogd serves `/catalogs/<name>/api/v1/all` as JSONL (Range requests honoured, no bearer token required over the in-cluster Service) and returns 404 for `/api/v1/metas` and GraphQL; there is no Route. The three default `ClusterCatalog`s (Red Hat -100, certified -200, community -400; no marketplace catalog on this cluster) resolve `:v5.0` tags to digests, and the Red Hat catalog carries all six RHWA packages with `replaces` plus `skipRange` edges, `olm.csv.metadata` bundles, digest bundle images and no `olm.maxOpenShiftVersion` property. OLM Classic (`catalog-operator`, `olm-operator`, `packageserver`) still runs alongside OLM v1 on 5.0, so the Classic-to-OLM v1 migration experiment remains applicable. No OLM v1 console plugin is registered.

What the inspection could not settle: no `ClusterExtension` existed and none was created, so the server-side-apply field manager names, the Helm-release versus revision storage, proxy and trusted-CA injection into extension Deployments (the cluster proxy was unset anyway), the "already exists … cannot be managed" message and the finalizer-blocked CRD deletion behaviour still need a mutating experiment on a disposable 5.0 cluster.

## Open questions and gaps the notes could not resolve

The notes leave a set of questions that the implementation should either test on a disposable cluster or treat as unknown. No primary source maps each OpenShift minor to a specific operator-controller tag; by feature-gate inventory `release-4.20` resembles upstream v1.4/v1.5, `release-4.21` v1.6–v1.8 and `release-4.22` v1.9/v1.10, but that is inference ([release-4.22 features.go](https://github.com/openshift/operator-framework-operator-controller/blob/release-4.22/internal/operator-controller/features/features.go)). Which OpenShift release adopts the `spec.serviceAccount` deprecation is undocumented; the 4.22 docs still require it, and the repository's own `test/olmv1/README.md` records that on an OCP 5.0.0-ec.5 cluster the field was ignored with a warn-only admission policy, which is the project's evidence rather than a Red Hat statement and should be re-verified when 5.0 ships. A read-only check of the OCP 5.0 rc5 test cluster on 2026-10-10 confirmed it: the field is documented as ignored, the warn-only policy `clusterextension-serviceaccount-deprecated` fires on create and update, and operator-controller is bound to `cluster-admin` (see the live-cluster section above); a Red Hat documentation statement is still outstanding. Whether OLM v1 on OpenShift injects the cluster-wide proxy variables or the trusted CA bundle into extension Deployments is stated nowhere; the notes treat it as "not provided" pending a cluster check. Whether the major-zero automatic-upgrade restrictions apply when an explicit `replaces` edge exists under `CatalogProvided` was not confirmed, and the behaviour when both `channels` and `version` are set and nothing new matches is undocumented. The exact string of the "already exists ... cannot be managed by operator-controller" error per release and the server-side-apply field manager names were not verified, nor was what happens when a CR finalizer blocks CRD deletion during `ClusterExtension` removal. No CRD-retention option exists and none is dated. On the catalog side, whether catalogd honours an image index (manifest list) by selecting a platform, whether a mounted `registries.conf` with `insecure = true` is honoured for plain-HTTP registries, whether `/api/v1/metas` is enabled on any OpenShift release (its gate `NewOLMCatalogdAPIV1Metas` is TechPreview), which `opm` version each OpenShift release embeds, and whether `opm render` surfaces an `olm.constraint` placed in `metadata/properties.yaml` into the FBC bundle properties are all unverified. Whether OCP 4.20+ still honours `olm.maxOpenShiftVersion` is supported by the 4.21 `html-single` Extensions guide text but the per-chapter page appears to have dropped it, so a cluster test is cheap insurance. Finally, no OLM v1-specific validator exists in operator-sdk, operator-framework/api or preflight, Red Hat's certification pipeline exercises only OLM Classic, no public Red Hat "OLM v1 readiness" checklist or KCS article was found, and the Boxcutter runtime's enablement state on 4.21 TechPreview clusters is ambiguous between the feature-gate definition and the downstream Helm values ([experimental.yaml](https://github.com/openshift/operator-framework-operator-controller/blob/main/openshift/helm/experimental.yaml)).

## Conclusion

The work to make WAO installable with OLM v1 is almost entirely outside the Go code and the CSV: an FBC build that replaces the SQLite-era `opm index add` target and the ConfigMap `CatalogSource`, a `ClusterCatalog`, a product-grade version of the installer RBAC the repository already generates, a namespace recipe, and user documentation that is honest about CRD deletion and the absence of migration. The umbrella design that looked like a liability under classic OLM, where WAO rather than the CSV owns the component Deployments and webhooks, turns out to be the reason WAO installs on OCP 4.18 and 4.19 at all, since OLM v1 only ever sees a webhook-free bundle. The same design concentrates risk in two places OLM v1 polices strictly: every component bump is a CRD upgrade subject to the upgrade-safety preflight, and the single-owner rule makes any leftover medik8s CRD a hard install failure.

The implementer should treat kind as the place to prove the catalog, graph and upgrade mechanics, and a disposable OpenShift cluster as the only place to prove RBAC, because upstream v1.12.0 runs as cluster-admin and will never report a missing installer permission. Version WAO as `1.0.0` rather than `0.1.0` before publishing anything to a shared catalog, keep `spec.serviceAccount` in the manifests until an OpenShift release demonstrably ignores it, and plan for the field's removal as a documentation change rather than a code change.
